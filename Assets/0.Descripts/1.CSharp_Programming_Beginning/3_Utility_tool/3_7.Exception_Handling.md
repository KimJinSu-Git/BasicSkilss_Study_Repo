# [실용 도구] 7. 예외 처리 (Exception Handling)

## 1. 예외(Exception)란?
중단점으로 잡는 버그가 '내가 코드를 잘못 짠 것'이라면, 코드를 완벽하게 짜도 **외부 환경에 의해 막을 수 없는 오류**가 있습니다.\
(예: 사용자가 숫자를 넣으라는 곳에 "안녕"이라고 적음, 세이브 파일이 삭제됨, 인터넷 연결이 끊김 등)

이러한 상황들은 코드가 틀려서가 아니라 바깥세상이 예상과 달라서 생깁니다. 이때 프로그램이 그 자리에서 멈추고 튕겨버리는(Crash) 것을 막기 위한 장치가 바로 **예외 처리**입니다.

> **곡예사와 안전망**
> * **`try`** : 곡예사가 줄타기를 하는 구역. 언제 떨어질지 모르는 **위험한 구간**을 감쌉니다.
> * **`catch`** : 곡예사가 떨어졌을 때 받아내는 **안전그물**입니다. (어떤 종류의 사고를 받아낼지 정할 수 있습니다.)
> * **`finally`** : 공연이 성공했든, 그물로 떨어졌든, 퇴근하기 전에 **반드시 해야 하는 뒷정리(청소)** 입니다.
> * **`throw`** : "도저히 공연을 계속할 수 없다!"고 판단될 때, 곡예사가 스스로 안전요원을 부르는(예외를 던지는) 행위입니다.

**왜 필요한가?**\
1시간 동안 진행한 게임에서 아이템 수량을 잘못 입력했다고 게임 창이 닫혀버린다면, 그것은 오류 이전의 '설계 실패'입니다. 예외 처리는 게임이 꺼지는 대신 **"잘못된 입력입니다. 다시 시도해 주세요"라고 부드럽게 안내할 기회**를 줍니다.

## 2. 핵심 요약 (Rider/VS 공통)

| 키워드 | 한 줄 설명 |
| :--- | :--- |
| **`Exception`** | 모든 예외 객체의 최상위 부모 타입. 에러 메시지와 추적 경로(StackTrace)를 가짐 |
| **`try`** | 실패할 가능성이 있는(외부 자원을 다루는) 코드를 감싸는 블록 |
| **`catch`** | 특정 예외 타입을 낚아채서 프로그램 종료를 막고 대신 수습하는 블록 |
| **`finally`** | `try` 성공 여부나 `return`에 상관없이 **무조건 마지막에 실행되는 블록** |
| **`throw`** | 현재 메서드에서 수습 불가함을 알리며, 호출자(부른 쪽)에게 폭탄을 던지는 문장 |
| **전파 (Propagation)** | `catch`가 없으면 폭탄은 호출 스택을 계속 타고 올라가며, 끝까지 없으면 게임이 꺼짐 |

## 3. 세부 개념 및 원리

### 3.1 예외는 호출 스택을 거슬러 올라갑니다
예외가 터지면 그 줄에서 즉시 실행이 멈추고, 자신을 부른 부모 메서드 방향으로 되돌아가며 자기를 받아줄 `catch` 그물을 찾습니다.
```csharp
void Main() {
    try { Step1(); }
    catch (IndexOutOfRangeException) { Console.WriteLine("잡았다"); }
}
void Step1() { Step2(); }
void Step2() {
    int[] arr = new int[3];
    arr[5] = 100; // 여기서 폭탄(예외) 생성. Step1을 뚫고 Main의 catch 그물로 날아감
}
```

### 3.2 `catch`를 여러 개 달기 (구체적인 것부터)
상황마다 다르게 대응하려면 `catch`를 여러 개 씁니다. 위에서부터 검사하므로 **반드시 좁고 구체적인 예외부터 잡고, 마지막에 만능 그물(`Exception`)을 쳐야 합니다.**
```csharp
try
{
    int n = int.Parse(Console.ReadLine());
    Console.WriteLine(100 / n);
}
catch (FormatException)       // 구체적인 그물 1
{
    Console.WriteLine("숫자만 입력하세요");
}
catch (DivideByZeroException) // 구체적인 그물 2
{
    Console.WriteLine("0으로는 나눌 수 없어요");
}
catch (Exception ex)          // 만능 그물 (반드시 맨 아래에)
{
    // 꿀팁: ex.ToString()을 쓰면 타입, 메시지, 호출 스택 경로까지 완벽하게 한 방에 출력해 줍니다.
    Console.WriteLine($"예상치 못한 에러: {ex.ToString()}"); 
}
```

### 3.3 `finally` : 어느 길로 가도 반드시 지나간다
`try`가 무사히 성공했든, `catch`로 터졌든, 심지어 **`try` 안에서 `return`을 만나 메서드를 빠져나가려 해도 `finally`는 무조건 실행**됩니다. 주로 열어둔 파일이나 네트워크를 닫을 때(자원 해제) 씁니다.

### 3.4 `throw` : 내가 알리는 쪽이 될 때
메서드가 도저히 임무를 완수할 수 없는 엉뚱한 값을 받았을 때, 억지로 진행하지 말고 폭탄(`throw`)을 던져 호출자에게 경고합니다.

```csharp
static void SetAge(int age)
{
    // 나이가 음수면 조용히 무시하는 대신, 에러를 던져서 부른 쪽이 수정하게 강제함
    if (age < 0)
        throw new ArgumentOutOfRangeException(nameof(age), "나이는 음수일 수 없습니다.");

    Console.WriteLine($"나이 {age} 설정 완료");
}
```

**[주의] 예외를 다시 던질 때 (Re-throw)**
```csharp
catch (Exception ex)
{
    // ❌ 최악의 실수: throw ex; 
    // 이렇게 쓰면 예외가 여기서 새로 생성된 것으로 처리되어, 진짜 에러가 난 깊은 원본 경로(StackTrace)가 싹 지워집니다

    // ⭕ 올바른 방법: throw;
    throw; // 원본 예외의 증거(호출 스택)를 그대로 보존한 채 다시 위로 던집니다.
}
```

## 4. 실전 활용 예시 (상점 시스템 설계)

객체 지향의 원칙에 따라, **'예외를 판별하고 던지는 쪽(Model)'** 과 **'예외를 잡아서 유저에게 텍스트로 보여주는 쪽(UI)'** 을 완벽하게 분리한 예제입니다.

```csharp
// 1. [상점 시스템] 데이터의 무결성만 검사하고, 문제가 생기면 가차 없이 예외를 던짐
public class Shop
{
    private Item[] _stock;
    public Shop(Item[] items) { _stock = items; }

    public Item GetItem(int index)
    {
        if (_stock == null || _stock.Length == 0)
            throw new InvalidOperationException("상점에 물건이 하나도 없습니다.");

        if (index < 0 || index >= _stock.Length)
            throw new ArgumentOutOfRangeException(nameof(index), "존재하지 않는 상품 번호입니다.");

        return _stock[index];
    }
}

// 2. [UI 로직] 예외를 안전하게 잡아내어 유저에게 친절한 문구로 안내함
class Program
{
    static void Main()
    {
        Shop shop = new Shop(new Item[] { new Item("약초"), new Item("장검") });
        Console.Write("살 물건 번호: ");

        // 1차 방어: 단순한 입력 오타는 예외 처리(try-catch)가 아니라 TryParse로 가볍게 막는다.
        if (!int.TryParse(Console.ReadLine(), out int index))
        {
            Console.WriteLine("번호를 숫자로 똑바로 입력하세요.");
            return;
        }

        // 2차 방어: 로직 상의 오류(재고 없음, 범위 초과)는 예외 처리로 잡는다.
        try
        {
            Item picked = shop.GetItem(index);
            Console.WriteLine($"{picked.Name} 구매 완료");
        }
        catch (ArgumentOutOfRangeException)
        {
            // 시스템 에러 메시지 대신 유저 친화적인 메시지 출력
            Console.WriteLine("구입 실패 — 그런 번호의 물건은 없습니다."); 
        }
        catch (InvalidOperationException ex)
        {
            // 상점에서 던진 세부 메시지를 그대로 보여줌
            Console.WriteLine($"구입 실패 — {ex.Message}");
        }
    }
}
```

## 5. Unity에서의 예외 처리

콘솔 프로그램은 예외가 터지면 검은 창이 꺼지지만, **유니티 게임은 죽지 않습니다.**\
유니티는 거대한 무한 루프이므로, `Update` 안에서 에러가 터지면 **"해당 프레임의 그 스크립트 실행만 끊기고, 다음 프레임에 또 똑같은 에러를 내며 계속 돌아갑니다."**

이 때문에 유니티에서는 반쪽짜리 UI가 남거나 캐릭터가 공중에 멈추는 기괴한 버그가 발생합니다.

### 5.1 어디에 `try-catch`를 쳐야 할까?
* **⭕ 감싸는 곳 (경계선)**: 세이브 파일 읽기/쓰기, 서버 네트워크 통신, JSON 파싱 등 **외부 데이터가 유입되는 불안정한 지점**.
* **❌ 감싸지 않는 곳**: `Update` 문 전체, 배열 인덱스 검색, `null` 검사.
    * 예외 처리 블록은 일반 `if`문 보다 성능 코스트가 비쌉니다. 매 프레임 도는 곳에 떡칠하면 성능이 크게 떨어집니다. `if (target == null) return;` 처럼 단순 조건문으로 막는 것이 훨씬 빠릅니다.

### 5.2 유니티 전용 에러 로깅
```csharp
try { LoadSaveData(); }
catch (Exception ex)
{
    // 내가 정의한 커스텀 에러 문구를 콘솔에 빨간색으로 출력
    Debug.LogError($"[세이브 시스템] 로드 실패: {ex.Message}"); 
    
    // 에러 타입과 전체 호출 경로(StackTrace)를 콘솔에 출력 (디버깅용)
    Debug.LogException(ex); 
}
```

## 6. 문법 : `using` 블록 (IDisposable)

파일을 열거나 DB에 연결하면 반드시 닫아주어야(자원 해제) 메모리 누수가 발생하지 않습니다. 이를 위해 항상 `try-finally`를 썼지만, 코드가 너무 길어집니다.\
이를 해결하기 위해 C#은 **`using` 문**을 지원합니다.

```csharp
// [과거의 방식]
FileStream fs = null;
try 
{ 
    fs = new FileStream("save.txt", FileMode.Open); 
    // 파일 읽기...
}
finally 
{ 
    if (fs != null) fs.Dispose(); // 무조건 파일 닫기
}

// [C#의 방식 (using 블록)]
// using 블록을 벗어나는 순간, 에러가 나든 안 나든 닷넷이 알아서 Dispose()를 호출해 줍니다
using (FileStream fs = new FileStream("save.txt", FileMode.Open))
{
    // 파일 읽기...
} // 이 괄호를 빠져나갈 때 자동으로 안전하게 파일이 닫힘.
```

## 7. 실습 문제 및 복습

**Q1. `try` 안에서 `return`을 만나 메서드를 빠져나갈 때, `finally` 블록의 코드는 실행될까요?**
> **네, 반드시 실행됩니다.** `try` 구문 내에서 `return`을 만나 값을 반환하려 해도, 메서드를 완전히 빠져나가기 직전에 닷넷 런타임이 무조건 `finally` 블록으로 점프하여 코드를 실행한 뒤에야 메서드 호출을 최종 종료합니다.

**Q2. `catch (FormatException)`과 `catch (Exception)`을 함께 쓸 때 순서를 뒤집으면 어떻게 되나요?**
> 컴파일 에러(`CS0160`)가 발생합니다. `Exception`은 모든 예외의 조상(최상위 부모)이므로, 맨 위에 두면 쏟아지는 모든 에러를 혼자 다 낚아채어 아래쪽에 있는 구체적인 `catch` 블록들은 영원히 실행될 수 없는 '데드 코드(Dead Code)'가 되기 때문입니다.

**Q3. `int.Parse` 대신 `int.TryParse`를 사용하는 것이 예외 처리 관점에서 좋은 이유는?**
> 유저가 키보드 오타를 내는 것은 매우 빈번하게 일어나는 '예상 가능한 분기'입니다. 예외 처리(`try-catch`)는 성능(CPU 코스트)을 꽤 소모하는 무거운 작업이므로, 가벼운 `TryParse`(성공/실패를 `bool`로 반환)를 사용하는 것이 성능상 압도적으로 유리합니다.

## 8. 주의사항 및 안전 습관

* **빈 `catch { }`는 사형 선고다**: 에러가 났는데 아무 로그도 남기지 않고 꿀꺽 삼켜버리는 것은, 훗날 며칠 밤을 새우게 만드는 최악의 버그를 은폐하는 행위입니다. 최소한 `Debug.LogError`라도 남기세요.
* **`throw ex;` 금지**: 예외를 다시 던질 때는 무조건 **`throw;`** 만 적으세요. 그래야 에러가 발생한 원본 파일의 라인 넘버(StackTrace)가 유지됩니다.
* **예외를 로직 흐름 제어에 쓰지 마라**: "이 함수가 끝났음을 알리기 위해 완료 Exception을 던지자" 같은 짓은 절대 금물입니다. 예외 처리는 정말로 '예외적인 심각한 오류 상황'에만 사용해야 합니다.
