# [실용 도구] 6. 중단점 (Breakpoint)과 디버깅 (Rider 환경)

## 1. 중단점(Breakpoint)이란?
분명히 생각한 대로 짰는데 프로그램이 엉뚱하게 도는 순간이 반드시 옵니다. 코드 속의 벌레(Bug)를 찾아 없애는 일을 **디버깅(Debugging)** 이라 부르며, 이 일에 쓰는 가장 강력하고 기본적인 도구가 바로 **중단점**입니다.

> **손전등 vs 시간 정지 마법**
> * **`Debug.Log(로그)`** : 어두운 방에 손전등을 한 번 비추는 일입니다. 내가 비춘 딱 그 자리의 값만 볼 수 있습니다. 원인이 어디 있는지 모를 때는 방 전체에 손전등 수십 개를 달아야 해서 코드가 지저분해집니다.
> * **중단점 (Breakpoint)** : 방 전체의 **시간을 통째로 멈추는 마법**입니다. 멈춘 시간 동안 모든 변수, 모든 호출 흐름(스택)을 내 마음대로 샅샅이 뒤져볼 수 있습니다.

**왜 필요한가?**\
버그를 잡을 때 코드를 '고치는' 시간은 1분도 안 걸립니다. 99%의 시간은 **"어디가 잘못됐는지 찾는 시간"** 에 쓰입니다. 중단점은 코드를 고치지 않고 프로그램의 멱살을 잡아 멈춰 세운 뒤, 현재 상태를 완벽하게 검사하여 다음 추적 구간을 좁혀주는 최고의 수사 도구입니다.

## 2. 핵심 요약 (Rider 기본 키맵 기준)

| 키워드 / 기능 | Rider 단축키 | 한 줄 설명 |
| :--- | :--- | :--- |
| **중단점 설정/해제**| `Ctrl + F8` | 코드 줄 번호 오른쪽 여백을 클릭하여 빨간 점 생성 |
| **디버그 실행**| `Alt + F5` | 디버그 모드로 게임을 실행. |
| **다음 중단점으로**| `F9` (Resume) | 멈춘 상태에서 누르면 다음 중단점을 만날 때까지 달림 |
| **Step Over** | `F8` | 현재 줄을 실행하고 다음 줄로 감. (함수가 있어도 겉핥고 지나감) |
| **Step Into** | `F7` | 현재 줄에 함수(메서드)가 있다면 **그 함수 안으로 파고 들어감** |
| **Step Out** | `Shift + F8` | 들어온 함수가 멀쩡하다면, **남은 코드를 마저 실행하고 밖으로 빠져나옴** |
| **식 평가 (Evaluate)**| `Alt + F8` | 멈춘 상태에서 원하는 코드나 수식을 직접 실행해 보는 마법의 창 |

*(참고: Rider 설정에서 키맵을 'Visual Studio'로 변경했다면 F5/F10/F11로 동작합니다.)*

## 3. 세부 개념 및 실무 원리

### 3.1 가장 헷갈리는 규칙: "실행하기 직전"에 멈춘다
```csharp
int a = 10;
int b = 20;
int sum = a + b; // 여기에 중단점을 걸고 디버깅을 시작하면?

Console.WriteLine(sum);
```
에디터가 `int sum = a + b;`에 멈춰 있을 때, `sum`에 마우스를 올려보면 값은 `30`이 아니라 `0`입니다.
**중단점은 그 줄을 실행한 뒤가 아니라, "실행하기 직전"에 멈춥니다.** 결과를 보고 싶다면 `F8 (Step Over)`을 한 번 눌러 다음 줄로 내려가야 합니다.

### 3.2 값을 추적하는 Rider의 강력한 디버그 창
하단의 디버그(Debug) 탭에서 다음 기능들을 활용해 샅샅이 뒤집니다.
1. **인라인 힌트 (Inline Values)**: Rider의 최고 장점. 멈추는 순간 코드 에디터 변수 옆에 흐릿한 글씨로 현재 값이 자동으로 표시됩니다.
2. **변수 창 (Variables)**: 지금 멈춰 있는 메서드 내부의 모든 지역 변수와 `this` 객체의 상태를 트리 형태로 보여줍니다.
3. **식 평가 창 (Evaluate Expression - `Alt + F8`)**: 단순히 값을 보는 것을 넘어, 멈춘 시점에서 코드를 직접 타이핑해 실행해 볼 수 있습니다. (`player.Heal(50)`을 쳐서 강제로 회복시켜 볼 수도 있습니다!)
4. **프레임 창 (Frames / Call Stack)**: 지금 이 에러가 나는 메서드까지 **"어떤 경로를 타고 들어왔는지"** 를 역추적해서 보여줍니다. 잘못된 파라미터를 넘긴 진짜 범인을 찾을 때 필수입니다.

### 3.3 `Debug.Assert` : 소리 지르는 지뢰 설치하기
중단점은 에디터를 끄면 날아갑니다. 영구적인 검사 장치를 코드에 박아두고 싶을 때 씁니다.

```csharp
using System.Diagnostics;

public void TakeDamage(int damage)
{
    // 이 코드를 호출하는 개발자가 실수로 데미지를 음수로 넘겼다면?
    // 즉시 게임 실행을 멈추고 에러 메시지를 뿜어냅니다
    Debug.Assert(damage >= 0, $"[버그] 데미지는 음수일 수 없습니다. 입력값: {damage}");
    
    _health -= damage;
}
```
> **[주의사항] Assert 안에서 값을 바꾸지 마라**\
> `Debug.Assert`는 개발(Debug) 빌드에서만 동작하고, 출시(Release) 빌드에서는 **컴파일러가 이 코드를 통째로 삭제**해버립니다. `Debug.Assert(myList.Remove(item));` 처럼 괄호 안에서 상태를 변경해버리면, 출시 버전에서는 로직 자체가 통째로 날아가 버리니 **읽기(비교) 연산만** 넣으세요

## 4. 디버깅 5단계 프로세스

초보자는 에러가 나면 코드부터 뚫어져라 봅니다. 코드 대신 아래 5단계 절차를 밟는 것이 좋습니다.

**[1단계] 증상을 표로 명확히 적는다.**\
"버그 났어요"가 아니라, 기대 동작과 실제 동작을 비교하여 문장으로 남깁니다.
* 기대: 스킬 사용 시 쿨다운 5초 유지
* 실제: 스킬 사용 후 인벤토리를 열었다 닫으면 쿨다운이 0이 됨 ➔ (인벤토리 창 여닫기가 단서임을 확정)

**[2단계] 재현 절차를 1, 2, 3번으로 적는다.**\
재현할 수 없는 버그는 고칠 수도, 검증할 수도 없습니다. 똑같은 버그를 100% 발생시키는 스텝을 확보하세요.

**[3단계] 실행 구간을 반(1/2)씩 쪼개며 중단점을 건다. (이진 탐색)**\
처음부터 `F8`을 누르며 100줄을 다 읽는 것은 하수입니다. 로직의 **절반(50번째 줄)** 에 중단점을 겁니다. 거기서 값이 멀쩡하면? 원인은 나머지 50줄 안에 있습니다. 탐색 구간이 절반씩 팍팍 줄어듭니다.

**[4단계] 원인의 개수를 미리 짐작한다.**\
증상 하나에 원인이 둘인 경우는 흔합니다. 예외(Error) 하나를 고쳤다고 디버깅을 끝내면 숨어있던 두 번째 논리 버그가 내일 다시 터집니다.

**[5단계] 증상만 가리는 반창고 수정은 악(Evil)이다.**\
예외가 난다고 `try-catch`로 덮어버리거나, 마지막에 `if (hp < 0) hp = 0;`으로 결괏값만 끼워 맞추는 것은 고름을 덮어두는 행위입니다. 반드시 근본 원인(Root Cause)을 잘라내야 합니다.

## 5. Unity + Rider 디버깅 꿀팁

Rider는 유니티 디버깅을 위해 완벽한 툴입니다.

### 5.1 Unity에 연결 (Attach to Unity Editor) 버튼
Rider 우측 상단을 보면 **유니티 로고 옆에 벌레(Bug)가 있는 버튼**이 있습니다.\
복잡한 설정 없이 이 버튼만 누르면, 유니티 에디터와 Rider가 즉시 디버깅 모드로 강력하게 연결됩니다

### 5.2 Error Pause (에러가 나는 찰나의 순간 박제하기)
`NullReferenceException` 같은 에러가 1초에 60번씩 쏟아질 때가 있습니다.\
유니티 **Console 창 상단의 `Error Pause` 버튼을 켜두세요.**\
에러가 발생하는 바로 그 프레임에 게임이 **자동으로 일시 정지(Pause)** 됩니다. 그 찰나의 순간에 Rider의 중단점을 걸고 씬을 샅샅이 뒤져 범인을 찾을 수 있습니다.

### 5.3 조건부 중단점 활용 (반복문과 Update의 구원자)
유니티 `Update()` 문에 그냥 중단점을 걸면 1초에 60번씩 멈춰서 디버깅이 불가능합니다.\
Rider에서 중단점(빨간 점)을 우클릭하면 **Condition(조건)** 을 입력할 수 있습니다.
* 조건식: `health - amount < 0`\
  이렇게 설정하면 수만 프레임이 정상적으로 돌다가, **오직 플레이어가 죽는 그 일격이 들어오는 프레임에만 정확히 에디터를 멈춰줍니다.**

### 5.4 `Debug.Log` vs 중단점 선택 기준
* **`Debug.Log` 사용**: 몬스터의 체력, 초당 이동 속도처럼 **"매 프레임 연속적으로 변하는 값의 패턴"** 을 모니터링하고 싶을 때.
* **중단점 사용**: "체력이 왜 갑자기 0이 됐지?" 처럼 **단 한 번 발생한 논리적 오류의 출처와 경로(Frames 창)** 를 역추적하고 싶을 때.

## 6. 실습 문제 및 복습 (Rider 환경)

**Q1. `F8 (Step Over)`과 `F7 (Step Into)`의 차이를 설명하고, `A() ➔ B() ➔ C()` 사슬에서 `C()` 안까지 들어갔다가 `C()`는 멀쩡하다고 판단했을 때 무엇을 눌러야 하는지 고르세요.**
> * **`F8 (Step Over)`**: 현재 줄을 실행하고 다음 줄로 갑니다. 함수가 있어도 통째로 실행해버리고 안으로 들어가지 않습니다.
> * **`F7 (Step Into)`**: 현재 줄에 함수가 있으면 그 함수 내부의 첫 줄로 파고 들어갑니다.
> * **답**: `C()`가 멀쩡하다면 **`Shift + F8 (Step Out)`** 을 누릅니다. 긴 반복문을 일일이 빠져나올 필요 없이, 즉시 `C()`를 마저 실행하고 호출했던 곳(`B()`)으로 쾌속 복귀합니다.

**Q2. 디버깅 중 배열이나 컬렉션 안에서 짝수인 항목만 골라서 필터링해 보고 싶습니다. 코드를 수정하고 재빌드하지 않고 Rider에서 이를 확인하는 가장 좋은 방법은?**
> 디버깅 모드로 멈춰있을 때 **`Alt + F8 (Evaluate Expression)`** 창을 열고, 식 입력란에 `myList.Where(x => x % 2 == 0).ToList()` 같은 LINQ 코드를 쳐서 직접 실행해 보면, 즉시 필터링된 결괏값을 확인할 수 있습니다.

**Q3. 아래 `TakeDamage` 메서드에서 데미지에 음수가 들어오면 체력이 회복됩니다. `Debug.Assert`를 어디에 어떻게 넣을지 쓰고, 예외(Exception)를 쓰지 않고 Assert를 쓰는 이유를 설명하세요.**
```csharp
using System.Diagnostics;

static int TakeDamage(int health, int damage)
{
    // 부르는 쪽 코드의 논리적 실수를 잡아내기 위해 메서드 맨 앞에 배치합니다.
    Debug.Assert(damage >= 0, $"피해량은 음수일 수 없다. damage={damage}");
    Debug.Assert(health >= 0, $"체력이 이미 음수다. health={health}");

    health -= damage;
    if (health < 0) health = 0;

    return health;
}
```
> **이유**: 음수 피해량이 들어오는 것은 유저의 키보드 입력 오류(예외 처리 대상)가 아니라, 이 코드를 호출하는 동료 개발자(또는 나)의 **논리적 오작동**이기 때문입니다. 배포판에서는 지워지더라도, 개발 도중에는 즉각적으로 멈추어 범인을 색출하게 만드는 `Assert`가 적합합니다.
