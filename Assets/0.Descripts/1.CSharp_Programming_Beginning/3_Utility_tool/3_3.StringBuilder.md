# [실용 도구] 3. 스트링빌더 (StringBuilder)

## 1. StringBuilder란?
`string`이 한 번 새기면 바꿀 수 없는 무거운 돌판이라면, **`StringBuilder`는 마음껏 쓰고 지울 수 있는 거대한 화이트보드**와 같습니다.\
문자열을 반복적으로 수정하거나 여러 조각을 합쳐 긴 텍스트를 만들 때, 불필요한 메모리 낭비 없이 최고 속도로 작업하기 위해 탄생한 클래스입니다.

> **돌판 깎기 vs 화이트보드 사진 찍기**
> * **`string + string` 연산** : 글자를 하나 추가할 때마다 기존 돌판을 버리고 더 큰 돌판을 가져와 처음부터 다시 깎는 엄청난 비효율이 발생합니다.
> * **`StringBuilder`** : 널찍한 화이트보드에서 글자를 마음껏 쓰고 지운 뒤, 모든 편집이 끝나면 마지막에 스마트폰으로 **찰칵 사진을 찍어 결과물(돌판, `string`)을 단 한 장만 생성**합니다.

**왜 필요한가?**\
반복문 안에서 10,000번 문자열을 `+`로 누적하면 10,000개의 임시 쓰레기 객체가 힙 메모리에 생깁니다. (가비지 컬렉터 폭주, 시간복잡도 $O(N^2)$). 반면 `StringBuilder`는 내부 배열(Buffer) 안에서 글자만 쓱쓱 덮어쓰기 때문에 수백 배 빠릅니다.

## 2. 핵심 요약

| 특징 | 한 줄 설명                                             |
| :--- |:---------------------------------------------------|
| **핵심 특징** | **가변(Mutable)** ➔ 객체 내용(버퍼)을 직접 수정 가능함             |
| **동작 원리** | 내부에 여유 공간을 가진 글자 배열(`char[]` 버퍼)을 보유함              |
| **사용 시기** | **반복문 안에서 텍스트를 누적할 때**, 거대한 텍스트를 조립할 때             |
| **사용 금지** | 1~3개 정도의 단순 단어 연결 (이때는 `$""` 보간이 훨씬 빠름)            |
| **최종 변환** | 모든 편집이 끝난 후 **`.ToString()`** 으로 최종 `string` 1개 생성 |
| **네임스페이스**| `using System.Text;` 필수                            |

## 3. 세부 개념 및 원리

### 3.1 내부 원리: Length와 Capacity
* **`Length`** : 현재 칠판에 적혀있는 실제 글자 수
* **`Capacity`** : 칠판의 전체 크기 (버퍼의 최대 용량)\
  글자를 추가하다가 `Length`가 `Capacity`를 초과하면, `StringBuilder`는 조용히 2배 더 큰 칠판을 새로 가져와 내용을 옮겨 적습니다. 이 재할당 횟수를 줄이기 위해 처음부터 `new StringBuilder(1000)`처럼 넉넉한 크기를 정해주는 것이 좋습니다.

### 3.2 주요 편집 메서드 (체이닝)
대부분의 메서드가 자기 자신(`StringBuilder`)을 다시 반환하므로, 마침표를 연달아 찍는 기차놀이(메서드 체이닝)가 가능합니다.
```csharp
StringBuilder sb = new StringBuilder();

sb.Append("Hi");               // 끝에 붙이기
sb.AppendLine(" Welcome.");    // 끝에 붙이고 줄바꿈(\n) 추가
sb.Insert(0, "[Start] ");      // 특정 위치에 끼워 넣기
sb.Replace("Hi", "Bye");       // 글자 교체하기
sb.Remove(0, 8);               // 특정 구간 지우기
sb.Clear();                    // 화이트보드 싹 지우기 (재사용의 핵심)

string result = sb.ToString(); // 최종 결과물을 string으로 뽑아내기
```

## 4. 코드로 보는 `string` vs `StringBuilder`

### 4.1 성능 차이의 극명한 예시
```csharp
// 비효율 (최악의 패턴) — 매 반복마다 새 string 객체가 힙에 버려짐
string slow = "";
for (int i = 0; i < 10000; i++)
{
    slow += i; // 1만 개의 쓰레기 객체 생성
}

// 효율 (권장 패턴) — 하나의 화이트보드(버퍼) 안에서 쓱쓱 적음
var sb = new StringBuilder();
for (int i = 0; i < 10000; i++)
{
    sb.Append(i); 
}
string fast = sb.ToString(); // 마지막에 단 1번만 string 생성
```

### 4.2 [주의] Append 안에서 쓰레기 만들지 않기
`StringBuilder`를 쓸 때 초보자들이 가장 많이 하는 실수입니다.
```csharp
var sb = new StringBuilder();
string name = "용사";
int level = 50;

// ❌ 잘못된 사용: 괄호 안의 보간($) 연산이 먼저 실행되어 임시 string 쓰레기가 생겨버림
sb.Append($"[Lv.{level}] {name}"); 

// ⭕ 올바른 사용: 조각조각 잘라서 체이닝으로 넘기면 쓰레기 생성 0% (Zero-Allocation)
sb.Append("[Lv.").Append(level).Append("] ").Append(name);
```

## 5. 실전 활용 예시 (게임 데이터 HTML 파싱)

인벤토리의 아이템 데이터를 HTML 테이블 형식으로 동적 조립합니다.

```csharp
using System.Text;
using System.Collections.Generic;

public class Product { public string Name; public int Price; }

public class HtmlGenerator
{
    public string CreateProductTable(List<Product> products)
    {
        // 넉넉하게 칠판 크기를 512자로 시작 (재할당 방지 최적화)
        var html = new StringBuilder(512); 
        
        html.AppendLine("<table>");
        html.AppendLine("  <thead><tr><th>Name</th><th>Price</th></tr></thead>");
        html.AppendLine("  <tbody>");

        foreach (var p in products)
        {
            html.Append("    <tr><td>").Append(p.Name).Append("</td><td>");

            // 비싼 아이템은 <strong> 태그로 강조
            if (p.Price >= 1000)
                html.Append("<strong>").Append(p.Price).Append("</strong>"); // 가비지 없는 체이닝
            else
                html.Append(p.Price);

            html.AppendLine("</td></tr>");
        }

        html.AppendLine("  </tbody></table>");

        // 칠판의 글자들을 사진 찍어서 string으로 반환
        return html.ToString(); 
    }
}
```

## 6. Unity에서의 완벽한 최적화 기법

UI 텍스트나 로그를 갱신할 때 `StringBuilder`를 매 프레임 `new`로 만들면 결국 그 화이트보드 자체도 쓰레기가 됩니다.\
**"화이트보드를 클래스 필드에 하나만 사두고, 지우개(`Clear()`)로 지워가며 평생 쓰는 패턴"** 이 최적화의 정석입니다.

```csharp
using UnityEngine;
using TMPro;
using System.Text;
using System.Collections.Generic;

public class InventoryUI : MonoBehaviour
{
    [SerializeField] private TMP_Text _inventoryText;
    public List<string> items = new List<string>();

    // 핵심: 화이트보드를 필드로 한 번만 생성해두고 평생 재사용합니다.
    private readonly StringBuilder _sb = new StringBuilder(256);

    public void RefreshUI()
    {
        _sb.Clear(); // 지우개로 칠판을 싹 지움 (메모리 해제가 아니라 인덱스만 0으로 돌려서 초고속)
        
        _sb.AppendLine("=== 인벤토리 ===");
        
        for (int i = 0; i < items.Count; i++)
        {
            _sb.Append("- ").AppendLine(items[i]); // 가비지 제로 타격
        }

        _inventoryText.text = _sb.ToString(); // 화면에 적용
    }
}
```

## 7. 실습 문제 및 복습

**Q1. `string`과 `StringBuilder`의 가변성 차이와, 그로 인해 발생하는 성능 차이를 설명하세요.**
> * **`string` (불변)**: 수정할 때마다 기존 것을 버리고 새 객체를 생성하므로 반복문 안에서 최악의 속도와 가비지(GC) 폭주를 유발합니다.
> * **`StringBuilder` (가변)**: 내부 버퍼 안에서 글자를 직접 덮어쓰므로 객체 생성이 거의 일어나지 않아 매우 빠릅니다.

**Q2. `StringBuilder`가 무조건 빠르니 항상 쓰자는 주장의 맹점은 무엇인가요?**
> 단순한 단어 1~3개를 합치는 작업에서는 `StringBuilder`라는 객체 자체를 힙에 올리는 비용(오버헤드)이 오히려 더 큽니다. 단순 연결은 `$"{first} {last}"` 보간 문자열이 내부적으로 최적화가 잘 되어 있어 더 빠르고 가독성도 좋습니다. **반복문 내에서의 누적 연산**에만 `StringBuilder`를 써야 합니다.

**Q3. `new StringBuilder(8000)`처럼 `Capacity`를 미리 크게 잡아두는 코드는 언제 유용할까요?**
> 대용량 텍스트(예: 거대한 로그 파일, 대규모 JSON 파싱 등)를 다룰 때 유용합니다. 내부 버퍼 용량을 초과하면 메모리를 2배 크기로 새로 할당하고 내용을 복사하는 이사 비용이 드는데, 최종 크기를 미리 예측해서 크게 잡아두면 이사(재할당)가 발생하지 않아 성능이 극대화됩니다.

## 8. 주의사항 및 안전 습관

* **`Append` 괄호 안에서 `$`나 `+`를 절대 쓰지 마라**: `sb.Append($"HP: {hp}");`는 임시 쓰레기를 만듭니다. `sb.Append("HP: ").Append(hp);` 처럼 기차놀이(체이닝)를 하세요.
* **`Update` 안에서 매번 `new StringBuilder()` 금지**: Unity에서 빈번하게 호출되는 로직은 클래스 최상단(필드)에 인스턴스 하나를 올려두고 `sb.Clear()`로 칠판을 재사용하세요.
* **`using System.Text;` 빼먹지 않기**: 이 네임스페이스를 선언하지 않으면 `StringBuilder`를 쓸 수 없습니다.
* **출력 전엔 항상 `ToString()`**: UI에 넣거나 로그를 찍을 때는 칠판 자체를 넘기면 안 됩니다. 반드시 `.ToString()`으로 스냅샷(string)을 찍어서 전달하세요.
