# [객체 지향] 5. 추상화 (Abstraction)

## 1. 추상화(Abstraction)란?
객체 지향 4대 원칙의 마지막인 추상화는 **내부의 복잡한 구현을 꽁꽁 감추고, 외부에 꼭 필요한 핵심 기능만 단순한 형태로 드러내는 것**을 말합니다.
즉, "이것이 무엇을 하는가(What)"만 보여 주고 "그것을 어떻게 하는가(How)"는 숨깁니다.

> **자동차 운전**
> * 운전자는 엔진의 폭발 행정도, 변속기가 기어를 바꾸는 복잡한 원리도 알 필요가 없습니다.
> * 단지 **핸들 · 페달 · 기어봉**이라는 단순한 조작부(인터페이스)만으로 "가속한다", "방향을 바꾼다"는 핵심만 다룹니다.
> * 자동차 내부의 복잡함은 운전자에게 완전히 감춰져 있습니다.

**왜 필요한가?**\
"모든 몬스터는 공격한다"는 사실이지만, 슬라임의 박치기와 드래곤의 브레스를 부모 클래스 한 곳에 모아서 다 써줄 방법은 없습니다.\
이때 부모가 빈 껍데기 함수를 만들고 "자식들아, 너희가 알아서 덮어쓰렴(virtual)" 하고 넘기면, 누군가 재정의를 깜빡했을 때 에러도 안 나고 가만히 서 있는 멍청한 드래곤이 탄생합니다.\
추상화(`abstract`)는 이 느슨한 약속을 **컴파일러가 강제하는 강력한 의무**로 바꿉니다. 부모는 이름만 정해두고, 자식이 채우지 않으면 아예 게임 실행(컴파일)조차 되지 않게 막아버립니다.

## 2. 핵심 요약

| 구분 | 한 줄 설명                                                          |
| :--- |:----------------------------------------------------------------|
| **핵심 개념** | **복잡성은 감추고 본질만 드러낸다** (Hide Complexity, Expose Essentials)      |
| **최종 목표** | 부르는 쪽(Main)이 자식의 구체적인 타입(Slime, Dragon)을 몰라도 공격 버튼 하나만 누르게 하기   |
| **추상 클래스** | 미완성된 뼈대가 섞인 부모 클래스. **절대 `new`로 직접 객체를 생성할 수 없음**               |
| **`abstract` 멤버** | 중괄호(`{ }`) 몸통이 없는 메서드. 자식은 반드시 **`override`로 몸통을 채워야 할 의무**가 생김 |
| **강제 시점** | 런타임(게임 중)이 아니라 **컴파일(빌드) 타임에 즉시 에러**로 잡아냄                       |
| **인터페이스 (Interface)**| 공통 필드조차 없고, 100% 밑그림(약속)으로만 이루어진 순수한 추상화 도구 |

## 3. 세부 개념 및 원리

### 3.1 추상 클래스 — 미완성인 채로 물려주기
`abstract` 키워드를 붙인 클래스는 그 자체로는 객체를 만들 수 없는 '미완성 설계도'입니다. 안에는 두 종류의 멤버가 섞여 있을 수 있습니다.
1. **일반 멤버** : 몸통이 다 채워져 있습니다. (체력 깎기 등 공통 로직. 자식이 그대로 물려받아 씁니다.)
2. **`abstract` 멤버** : 몸통(`{ }`)이 아예 없습니다. (자식이 반드시 자기만의 방식으로 채워 넣어야 합니다.)

```csharp
public abstract class Monster
{
    public int Hp { get; protected set; }

    // 1. 일반 메서드 (모든 자식이 이 코드를 그대로 공통 사용)
    public void TakeDamage(int amount) => Hp -= amount;

    // 2. abstract 멤버 (몸통 없이 세미콜론으로 끝남. 자식이 무조건 구현해야 함)
    public abstract void Attack(); 
}
```

### 3.2 단순 가상 함수(`virtual`)와 추상 함수(`abstract`)의 결정적 차이
```csharp
// ❌ 상황 A (virtual 사용): 드래곤 개발자가 재정의를 깜빡했다
public class Monster {
    public virtual void Attack() { /* 몬스터마다 다르니 일단 비워둠 */ }
}
public class Dragon : Monster {
    // override를 잊어버렸지만 컴파일러는 조용하다. 게임에 들어가면 드래곤이 공격을 안 함
}

// ⭕ 상황 B (abstract 사용): 컴파일러가 개발자의 멱살을 잡는다
public abstract class Monster {
    public abstract void Attack(); // 몸통 없음
}
public class Dragon : Monster {
    // 여기서 override void Attack()을 안 쓰면 바로 에러 줄이 그어지며 게임 실행 불가
}
```

### 3.3 추상 타입으로 묶어서 조종하기 (다형성의 완성)
추상 클래스는 `new`로 만들 수 없을 뿐, **타입(리모컨)** 으로는 얼마든지 쓸 수 있습니다.
```csharp
// 변수 타입은 미완성 '부모', 실제 메모리에 구워진 붕어빵은 완성된 '자식'
Monster[] monsters = { new Slime(), new Dragon() };

foreach (Monster m in monsters)
{
    // 부모 리모컨의 Attack() 버튼에는 알맹이가 없지만, 
    // 누르는 순간 실제 연결된 자식들의 화려한 공격 로직이 튀어나감
    m.Attack(); 
}
```

## 4. 실전 활용 예시 (도형 넓이 계산기)

공통 흐름(뼈대)은 부모가 꽉 잡고, 각자 달라지는 빈칸(공식)만 자식에게 채우라고 넘기는 실무의 표준 구조입니다. 이를 **템플릿 메서드 패턴(Template Method Pattern)** 이라고 부릅니다.

```csharp
public abstract class Shape
{
    public string Name { get; set; }

    // 1. 도형마다 넓이 공식이 다르므로 자식에게 짬때림
    public abstract double GetArea(); 

    // 2. 부모가 흐름을 통제: "자식이 채운 GetArea()를 가져와서 내가 출력"
    public void PrintInfo()
    {
        Console.WriteLine($"{Name}의 넓이: {GetArea():F2}");
    }
}

public class Circle : Shape
{
    public double Radius { get; set; }
    
    // 자식은 넓이 계산 공식만 성실하게 채워 넣으면 끝
    public override double GetArea() => Math.PI * Radius * Radius;
}

public class Rectangle : Shape
{
    public double Width { get; set; }
    public double Height { get; set; }

    public override double GetArea() => Width * Height;
}

// 사용 예시
Shape myCircle = new Circle { Name = "마법진", Radius = 5 };
myCircle.PrintInfo(); // 마법진의 넓이: 78.54
```

## 5. Unity 실무에서의 추상화

유니티에서 컴포넌트끼리 상속할 때는 추상 클래스를 굉장히 자주 씁니다.

### 5.1 인스펙터 노출과 뼈대 설계
```csharp
using UnityEngine;

// 미완성 컴포넌트이므로 Hierarchy의 게임 오브젝트에 직접 붙일 수 없습니다
public abstract class EnemyBase : MonoBehaviour 
{
    // 추상 클래스에 둔 [SerializeField]는 자식 컴포넌트의 인스펙터 창에 아주 잘 나타납니다.
    [SerializeField] protected int maxHp = 100;
    protected int currentHp;

    // 공격 방식만 자식에게 강제로 넘긴다.
    public abstract void Attack();
}
```

### 5.2 [꿀팁] `Start()` 호출 까먹음 방지 패턴
부모 클래스에 `protected virtual void Start()`를 두고 자식에서 `base.Start()`를 호출하라고 지시하면, 신입 팀원들은 100% 확률로 `base.Start()` 호출을 까먹어서 치명적인 버그를 냅니다.\
이를 막기 위해 **유니티 생명주기는 부모가 독점하고, 자식에게는 `abstract` 초기화 함수만 강제하는 패턴**을 씁니다.

```csharp
public abstract class SafeEnemy : MonoBehaviour
{
    // 부모가 Start()를 꽉 쥐고 못 고치게 막아버림 (virtual 아님)
    private void Start()
    {
        Debug.Log("부모의 공통 필수 초기화 로직 (절대 안 날아감)");
        
        // 부모가 자식의 초기화 코드를 불러줌
        OnInit(); 
    }

    // 자식은 무조건 이 함수를 채워야만 하므로, 실수할 여지가 아예 차단됨
    protected abstract void OnInit(); 
}

public class Goblin : SafeEnemy
{
    // base.Start()를 까먹을 걱정 없이 맘편히 내 할 일만 하면 됨
    protected override void OnInit()
    {
        Debug.Log("고블린 고유의 초기화 세팅 완료");
    }
}
```

## 6. 실습 문제 및 복습

**Q1. `abstract`로 선언한 메서드가 일반 메서드 및 `virtual` 메서드와 다른 점은 무엇인가요?**
> * **일반 메서드**: 부모가 몸통(`{ }`)을 다 짜놓고 자식은 그대로 물려 씁니다.
> * **`virtual` 메서드**: 부모가 몸통을 짜놨지만, 자식이 마음에 안 들면 **선택적**으로 덮어쓸(`override`) 수 있습니다.
> * **`abstract` 메서드**: 부모는 아예 몸통을 비워두고, 자식이 무조건 자기만의 방식으로 덮어쓰도록 **의무적으로 강제**합니다. (안 하면 컴파일 에러)

**Q2. 아래 코드에서 컴파일 에러가 나는 부분을 모두 찾고 이유를 설명하세요.**
```csharp
public abstract class Monster
{
    public abstract void Attack() { }   // (a)
}

public class Slime : Monster { }        // (b)

Monster m = new Monster();              // (c)
```
> * **(a)**: `abstract` 메서드는 몸통(`{ }`)을 가질 수 없습니다. `public abstract void Attack();` 처럼 세미콜론으로 끝내야 합니다.
> * **(b)**: `Slime`은 부모의 추상 메서드인 `Attack()`을 `override`하지 않았으므로 컴파일 에러가 납니다.
> * **(c)**: 추상 클래스(`Monster`)는 아직 뼈대만 있는 미완성 상태이므로 `new` 키워드를 사용해 객체로 실체화할 수 없습니다.

**Q3. 추상 클래스 `Weapon`을 만들고, 무기 이름과 `GetDamage()` (추상 메서드), 그리고 공통 출력 함수 `Describe()`를 설계하세요. 자식으로 `Sword`와 `Bow`를 만드세요.**
```csharp
public abstract class Weapon
{
    public string Name { get; set; }
    
    // 자식마다 계산식이 다르므로 던짐
    public abstract int GetDamage(); 

    // 부모가 뼈대(출력 형식)를 잡아둠
    public void Describe() 
    {
        Console.WriteLine($"[{Name}] 위력: {GetDamage()}");
    }
}

public class Sword : Weapon
{
    public override int GetDamage() => 50; // 고정 데미지
}

public class Bow : Weapon
{
    public float Distance { get; set; } = 10f;
    public override int GetDamage() => (int)(30 / Distance); // 거리에 반비례
}
```

## 7. 주의사항 및 안전 습관

* **모든 것을 추상 클래스로 만들지 마라**: 자식 클래스가 당장 1개밖에 없는데 "나중에 늘어날지도 몰라" 하면서 미리 추상 클래스로 쪼개는 것은 오버엔지니어링(YAGNI 원칙 위배)입니다. 최소 2~3개의 자식이 생기며 공통점이 보일 때 리팩토링하세요.
* **상속의 깊이는 얕게**: `추상 ➔ 추상 ➔ 구체` 처럼 계층이 깊어지면 스파게티 코드가 됩니다.
* **유니티 메시지(`Update`, `Start`)를 `abstract`로 만들지 마라**: 부모에 `abstract void Update();`를 파두면, 가만히 서 있는 돌멩이 몬스터도 억지로 빈 `Update` 함수를 만들어야 해서 유니티 엔진에 쓸데없는 성능 낭비(콜백 비용)를 유발합니다.
