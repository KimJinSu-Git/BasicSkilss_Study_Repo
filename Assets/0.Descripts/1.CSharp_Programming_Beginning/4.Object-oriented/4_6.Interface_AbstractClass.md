# [객체 지향] 6. 인터페이스와 추상 클래스 (Interface vs Abstract Class)

## 1. 인터페이스와 추상 클래스란?
둘 다 "구체적인 자식의 타입을 몰라도 묶어서 다룰 수 있게" 만드는 다형성의 핵심 도구입니다.\
플레이어, 적, 나무 상자를 각각 다른 코드로 때리는 대신 **"맞을 수 있는 것"** 이라는 공통 약속으로 묶으면, 새로운 몬스터가 추가되어도 때리는 코드는 단 한 줄도 고치지 않아도 됩니다.

> **미완성 설계도 vs 자격증**
> * **추상 클래스 (미완성 설계도)** : 뼈대(엔진·바퀴)는 이미 그려져 있고, 좌석 수 같은 세부 사항만 자식에게 강제로 채우게 합니다. (혈통을 물려줌, **IS-A**)
> * **인터페이스 (자격증)** : "운전을 할 수 있다"는 능력만 보증하는 계약서입니다. 그 사람이 트럭을 몰든 택시를 몰든, 운전 실력이 어떻든 상관하지 않습니다. 그 기능이 '존재함'만 강제합니다. (**CAN-DO**)

**한 문장 선택 규칙**
> 정체성("이것은 전투 개체다", IS-A)과 상태(필드)를 공유하면 ➔ **추상 클래스**\
> 능력("얘는 알림을 받을 수 있다", CAN-DO)만 약속하면 ➔ **인터페이스**

## 2. 핵심 요약

| 개념 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
| :--- | :--- | :--- |
| **의미** | ~이다 (`is-a`, 정체성) | ~할 수 있다 (`can-do`, 능력) |
| **특징** | 일부는 구현하고 일부는 비워 둔 미완성 부모 | 멤버의 이름만 적어둔 순수한 계약서 |
| **필드(상태) 보유** | **가능** (`protected int hp;` 등) | **불가능** (오직 프로퍼티와 메서드만 가능) |
| **기본 구현 (몸통)**| 자유롭게 가능 (`virtual` 또는 일반 메서드) | 원칙상 없음 (단, C# 8.0부터 제한적 허용) |
| **다중 상속/적용** | 부모는 오직 **하나만** 가질 수 있음 | 여러 개를 동시에 구현할 수 있음 (수평적 확장) |
| **MonoBehaviour**| 상속 가능 (인스펙터 노출 가능) | 상속 불가 (인스펙터 직렬화 불가능) |

## 3. 세부 개념 및 원리

### 3.1 `abstract`와 `virtual`의 강제성 차이
추상 클래스 안에서 자식에게 무언가를 넘겨줄 때 두 가지 선택지가 있습니다.

```csharp
public abstract class CombatEntity : MonoBehaviour
{
    // 1. abstract (강제) : 몸체가 없다. 자식이 무조건 구현해야 하며 빠뜨리면 컴파일 오류
    // "데미지를 받는 연출은 몬스터마다 다르니까 알아서들 짜와라"
    public abstract void TakeDamage(int damage);

    // 2. virtual (선택) : 기본 몸체가 있다. 자식은 덮어써도(override) 되고 그냥 써도 된다.
    // "회복은 어차피 피 차는 거니까 내가 짜둔 기본 코드를 써라. 특수한 놈만 덮어써라"
    public virtual void TakeHeal(int heal) { /* ... */ }
}
```

### 3.2 수직 구조(계보)와 수평 구조(능력)
* **추상 클래스는 수직입니다.** 부모-자식 계보를 만듭니다. 사람은 아빠가 두 명일 수 없듯 클래스도 부모가 하나뿐입니다.
* **인터페이스는 수평입니다.** 핏줄과 무관하게 능력을 덧붙입니다. 자격증은 여러 개를 딸 수 있습니다.
```csharp
// 정체성은 하나(CombatEntity), 능력은 여럿(저장 가능 + 상호작용 가능)
public class Player : CombatEntity, ISavable, IInteractable { }
```

### 3.3 인터페이스의 기본 구현 (C# 8.0+)
과거 인터페이스는 `{ }` 몸통을 가질 수 없었습니다. 하지만 인터페이스를 수십 개의 클래스가 구현 중일 때, 새로운 기능을 하나 추가하면 모든 클래스에서 컴파일 에러가 터지는 지옥이 펼쳐집니다.\
이를 막기 위해 **인터페이스도 기본 몸통을 가질 수 있도록 문법이 진화**했습니다.
```csharp
public interface IDamageable
{
    void TakeDamage(int damage);

    // C# 8.0+ 기본 구현 (Default Implementation)
    // 기존에 IDamageable을 상속받던 클래스들을 에러 내지 않고, 공짜로 기능을 추가해 줍니다
    void TakeTrueDamage(int damage) 
    {
        TakeDamage(damage); // 기본 로직
    }
}
```

## 4. 코드로 보는 인터페이스의 위력 (Observer 패턴)

HP가 바뀌었을 때 화면의 HP Bar UI와 텍스트 UI를 업데이트해야 합니다.\
이때 플레이어 코드가 `HpBarUI` 클래스를 직접 호출하면 **강한 결합(Spaghetti Code)** 이 발생합니다. 인터페이스를 쓰면 서로가 누군지 몰라도 완벽하게 통신할 수 있습니다.

```csharp
// 1. 약속(능력)을 정의: "이걸 달고 있으면 HP 변화를 받아볼 수 있다"
public interface IHpObserver
{
    void OnHpChanged(int currentHp, int maxHp); 
}

// 2. 계보가 전혀 다른 두 UI가 같은 능력을 구현함
public class HpBarUI : MonoBehaviour, IHpObserver
{
    public void OnHpChanged(int currentHp, int maxHp) { /* 체력바 게이지 채우기 로직 */ }
}

public class HpTextUI : MonoBehaviour, IHpObserver
{
    public void OnHpChanged(int currentHp, int maxHp) { /* "100/100" 텍스트 갱신 로직 */ }
}

// 3. 체력을 깎는 주체 (알리는 쪽은 누가 듣고 있는지 구체적 타입을 전혀 모른다)
public class PlayerHealth
{
    private List<IHpObserver> _observers = new List<IHpObserver>();

    public void RegisterObserver(IHpObserver observer) => _observers.Add(observer);

    public void TakeDamage(int damage)
    {
        // 체력 감소 로직...
        
        // 인터페이스의 능력만 믿고 전체에게 방송(Broadcast)한다
        foreach (var observer in _observers) 
        {
            observer.OnHpChanged(currentHp, maxHp);
        }
    }
}
```

## 5. 실전 활용 예시 (폭발 데미지 처리)

액션 게임에서 플레이어, 슬라임, 나무 상자가 모두 폭발 데미지를 받습니다.\
셋의 핏줄(부모)은 제각각이지만 **"맞을 수 있다(IDamageable)"** 는 능력은 같습니다.

```csharp
public interface IDamageable
{
    void TakeDamage(int damage);
}

public class Crate : MonoBehaviour, IDamageable          // 정체성 : 맵 사물
{
    public void TakeDamage(int damage) => Destroy(gameObject); // 맞으면 부서짐
}

public class Slime : CombatEntity, IDamageable           // 정체성 : 전투 개체
{
    public override void TakeDamage(int damage) { /* 피 깎이고 죽는 애니메이션 */ }
}

// 범위 공격 (무엇이 들어 있든 정체성은 신경 쓰지 않는다)
public class Explosion : MonoBehaviour
{
    private void Explode(Collider2D[] hits)
    {
        foreach (var hit in hits)
        {
            // "너 혹시 맞을 수 있는 애(IDamageable)니?"
            if (hit.TryGetComponent(out IDamageable target))
            {
                target.TakeDamage(30);
            }
        }
    }
}
```

## 6. Unity 실무에서의 팁과 한계

유니티 엔진의 직렬화(Serialization) 시스템 한계 때문에 인터페이스 사용 시 고민이 발생합니다.

### 6.1 인터페이스는 인스펙터에 안 뜬다
```csharp
// 유니티 인스펙터 창에 아예 노출되지 않아서 프리팹을 드래그 앤 드롭 할 수 없음
[SerializeField] private IDamageable _target; 
```

### 6.2 해결책 1 : 런타임에 찾기 (유연하지만 무거움)
앞선 폭발 예시처럼 `GetComponent<IDamageable>()`로 런타임에 코드로 찾아옵니다. 가장 객체 지향적인 정석입니다.

### 6.3 해결책 2 : 구체 타입 노출 + `OnValidate` 방어 (에디터 친화적)
기획자가 인스펙터에서 편하게 조작해야 한다면, 일단 `MonoBehaviour`의 구체 타입으로 받되, 에디터 단에서 방어 코드를 짜는 꼼수를 씁니다.
```csharp
public class AutoTurret : MonoBehaviour
{
    // 1. 인스펙터 노출용 (기획자가 드래그 앤 드롭 하라고 놔둠)
    [SerializeField] private MonoBehaviour _targetObj; 
    
    // 2. 내부 로직 처리용 인터페이스
    private IDamageable _targetInterface;

    // 스크립트가 로드되거나 인스펙터 값이 바뀔 때 유니티 에디터가 호출해 주는 함수
    private void OnValidate()
    {
        if (_targetObj != null)
        {
            // 기획자가 드래그한 오브젝트가 IDamageable 자격증이 있는지 검사
            _targetInterface = _targetObj as IDamageable;
            
            if (_targetInterface == null)
            {
                Debug.LogError("여기에 넣은 오브젝트는 데미지를 받을 수 없는 녀석입니다");
                _targetObj = null; // 강제로 비워버림 (실수 방지)
            }
        }
    }
}
```

## 7. 실습 문제 및 복습

**Q1. `abstract` 메서드와 `virtual` 메서드의 차이를 "부모의 몸체"와 "자식의 의무" 측면에서 설명하세요.**
> * **`abstract`**: 부모 쪽에 몸체(`{ }`)가 없습니다. 자식은 무조건 `override`하여 몸체를 만들어야 할 **강제적 의무**가 생깁니다. (안 하면 컴파일 에러)
> * **`virtual`**: 부모 쪽에 기본 몸체가 있습니다. 자식은 원한다면 덮어써도 되지만, 귀찮으면 그냥 부모 것을 그대로 써도 되는 **선택적 권리**입니다.

**Q2. 인터페이스에 `private int hp;` 같은 상태(필드) 변수를 선언할 수 없는 이유는?**
> 인터페이스는 "이런 기능이 있다"는 **능력(행동)만을 보증하는 순수한 약속**의 자리이지, 데이터를 보관하는 깡통이 아니기 때문입니다.  
> 또한 한 클래스가 여러 인터페이스를 상속받을 수 있는데, 인터페이스마다 각자 필드를 가져버리면 이름이 겹쳤을 때 극심한 충돌(죽음의 다이아몬드 문제)이 발생합니다.

**Q3. 다음 요구사항을 추상 클래스와 인터페이스 중 무엇으로 설계할지 고르고 이유를 적으세요.**
* **(a) "모든 몬스터는 HP 필드와 이동 속도 필드를 가진다."**
* **(b) "이 오브젝트는 세이브/로드 시스템에 저장 가능하다. (ISavable)"**
> * **(a) 추상 클래스**: 상태(필드)를 가져야 하며 모든 몬스터가 '정체성'을 공유하기 때문입니다.
> * **(b) 인터페이스**: 상태를 가질 필요 없이 "저장된다"는 '능력'만 부여하면 되며, 저장 대상이 몬스터일 수도, 아이템일 수도, UI 세팅일 수도 있기 때문에 수평적으로 붙이는 인터페이스가 완벽합니다.

## 8. 주의사항 및 안전 습관

* **인터페이스 이름은 무조건 `I`로 시작하라**: `IDamageable`, `IInteractable`, `IEnumerable` 등 맨 앞에 대문자 I를 붙이는 것은 닷넷(.NET) 생태계의 절대적인 네이밍 컨벤션입니다.
* **`TryGetComponent`를 사랑하라**: 유니티에서 인터페이스를 가진 컴포넌트를 찾을 때는 `if (hit.TryGetComponent(out IDamageable target))` 패턴을 쓰세요. 에러도 안 나고 성능도 가장 빠릅니다.
* **인터페이스를 너무 뚱뚱하게 만들지 마라 (ISP 원칙)**: `IMonster` 인터페이스 하나에 `Attack()`, `Move()`, `Talk()`, `Fly()`를 다 때려 넣으면, 날지 못하는 슬라임도 억지로 `Fly()` 함수를 껍데기만 만들어야 합니다. 능력을 잘게 쪼개는 것이 좋은 설계입니다.
* **다중 상속의 유혹에 빠지지 마라**: C#이 클래스 다중 상속을 막아둔 데는 이유가 있습니다. 기능이 여러 개 필요하면 하나는 추상 클래스로, 나머지는 인터페이스 여러 개를 붙여서 조립하세요.
