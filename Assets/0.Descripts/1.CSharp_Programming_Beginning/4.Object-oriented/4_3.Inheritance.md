# [객체 지향] 3. 상속 (Inheritance)

## 1. 상속(Inheritance)이란?
객체 지향의 두 번째 원칙인 상속은 현실 세계의 분류 체계를 코드로 옮긴 개념입니다.\
'개'는 '포유류'의 모든 특징을 가지면서 자신만의 특징(멍멍 짖기)을 더합니다. 즉 **"개는 포유류이다(Dog is a Mammal)"** 라는 문장이 성립합니다. 이 관계를 **is-a 관계**라고 부릅니다.

> **가계도와 유산 상속**
> * 자식은 부모로부터 외모(필드)와 습관(메서드)을 고스란히 물려받습니다.
> * 자식은 거기에 더해 자신만의 새로운 특징을 추가할 수 있습니다.
> * 자식은 부모가 하던 일을 그대로 쓰기도 하고, 자기 방식대로 덧붙여서 발전시키기도 합니다.

**왜 필요한가?**\
`Goblin`, `Slime`, `Orc` 클래스를 각각 따로 만들면 `Hp`, `Move()`, `Attack()` 같은 공통 코드가 통째로 복제됩니다. 공격 공식이 바뀌면 세 곳을 다 고쳐야 하고, 하나라도 빠뜨리면 끔찍한 버그가 됩니다.\
공통 부분을 부모인 `Monster`에 한 번만 쓰고 자식들이 물려받게(상속) 하면, **고칠 자리가 한 곳으로 모이고 자식은 자기만의 차별점(특수성)만 구현하면 됩니다.** (코드 재사용의 극대화)

## 2. 핵심 요약

| 구분 | 한 줄 설명 |
| :--- | :--- |
| **핵심 개념** | **코드 재사용 + 확장**. 부모의 멤버를 물려받고 자식만의 멤버를 추가 |
| **is-a 관계** | 'A는 B의 한 종류이다'가 완벽히 성립할 때만 상속 사용 (`Warrior is a Character`) |
| **용어** | 부모 = 기반 / 상위 / Base / Super ➔ 자식 = 파생 / 하위 / Derived / Sub |
| **문법** | `class 자식클래스 : 부모클래스` (콜론 `:` 하나로 연결) |
| **물려받는 것**| 부모의 `public`, `protected` 멤버. (`private`은 물려받지만 자식이 직접 만질 수 없음) |
| **`base(...)`**| 자식 생성자가 만들어지기 전, 부모 생성자를 먼저 호출하면서 데이터를 넘겨주는 자리 |
| **`base.멤버`** | 자식 안에서 부모 쪽의 오리지널 메서드 구현을 콕 집어서 부르는 방법 |

## 3. 세부 개념 및 원리

### 3.1 상속의 구현 — 콜론(`:`) 하나
`class Child : Parent` 형태로 콜론을 찍어 부모를 지정합니다.\
**주의**: C#의 클래스는 부모를 **오직 하나만** 가질 수 있습니다 (단일 상속). `class Warrior : Character, Monster` 처럼 둘을 적으면 컴파일 에러가 납니다.

### 3.2 캡슐화의 확장: `protected` 접근 제한자
캡슐화 파트에서 배운 `public`과 `private` 사이에, 상속을 위한 **`protected`** 가 등장합니다. "외부에는 철저히 감추되, 내 자식에게만큼은 열어준다"는 뜻입니다.

| 접근 제한자 | 같은 클래스 (나) | 상속받은 자식 클래스 | 외부 (남) |
| :--- | :--- | :--- | :--- |
| **`public`** | O | O | O |
| **`protected`**| O | O | **X** |
| **`private`** | O | **X** | **X** |

### 3.3 생성자와 `base(...)` — 부모가 먼저 태어나야 한다
자식 객체가 `new`로 생성될 때, 자식보다 **부모의 생성자가 먼저 실행**되어야 합니다. 부모가 뼈대를 만들어 놔야 자식이 살을 붙일 수 있기 때문입니다.

```csharp
public class Child : Parent
{
    // 자식이 태어날 때 매개변수 s를 받아서, 부모(base) 생성자에게 먼저 토스해준다
    public Child(string s) : base(s) 
    {
        // 부모 생성이 끝나면 비로소 자식의 로직이 실행됨
    }
}
```
만약 `: base(...)`를 적지 않으면 컴파일러가 매개변수 없는 부모의 기본 생성자 `base()`를 몰래 부릅니다. 그런데 부모에게 기본 생성자가 없다면 에러가 납니다

### 3.4 덮어쓰기가 아니라 덧붙이기: `base.메서드()`
자식 클래스 안에서 `base.메서드()` 라고 적으면 부모가 가진 원래 기능을 그대로 실행할 수 있습니다.\
공통 처리(로그 출력, 마나 소모)는 부모에게 맡기고, 자식은 거기에 특수한 이펙트 연출만 더하는 설계가 가능해집니다.

### 3.5 업캐스팅 (Upcasting)
전사(`Warrior`)는 결국 캐릭터(`Character`)입니다. 따라서 **자식 객체는 부모 타입의 변수(리모컨)에 담길 수 있습니다.**
```csharp
// 부모 타입 배열 하나에, 전사와 마법사를 모두 담을 수 있습니다 (다형성의 시작)
Character[] party = new Character[2];
party[0] = new Warrior("전사"); // 업캐스팅 (자동)
party[1] = new Mage("마법사");  // 업캐스팅 (자동)

// 단, 부모 리모컨(party[0])으로는 자식 고유의 스킬(Slash) 버튼을 누를 수 없습니다.
```

## 4. 코드로 보는 상속의 위력

### 4.1 기본적인 상속과 `protected`
```csharp
public class Character
{
    public string Name { get; private set; } // 읽기는 누구나, 쓰기는 나만
    protected int hp; // 자식 클래스에게만 열어둔 필드

    public Character(string name, int hp)
    {
        this.Name = name;
        this.hp = hp;
    }

    public void Move() => Console.WriteLine($"{Name} 이동");
}

public class Warrior : Character // 상속
{
    public int Defence { get; private set; }

    // 자식 생성자 호출 시, 이름과 체력을 부모(base)에게 토스하여 초기화를 맡긴다
    public Warrior(string name, int hp, int defence) : base(name, hp)             
    {
        this.Defence = defence; // 자식 고유의 필드만 직접 초기화
    }

    public void Heal()
    {
        hp += 50; // 부모의 protected 필드이므로 자식도 마음대로 접근 가능
    }

    public void Slash() => Console.WriteLine($"{Name} 베기 (방어력: {Defence})");
}
```

## 5. 실전 활용 예시 (RPG 직업 설계)

모든 직업의 공통 상태와 행동을 부모 `GameCharacter`에 두고, 전사와 마법사는 자기만의 특성을 덧붙입니다.

```csharp
using System;

public class GameCharacter
{
    public string Name { get; private set; }
    public int Hp { get; private set; }

    public GameCharacter(string name, int hp)
    {
        Name = name; Hp = hp;
    }

    // virtual: "자식들아, 원한다면 이 메서드를 너희 방식대로 재정의(override) 해도 좋다"
    public virtual void Attack()
    {
        Console.WriteLine($"[공통] {Name}이(가) 공격 준비 자세를 취합니다.");
    }
}

public class Warrior : GameCharacter
{
    // 전사의 기본 체력(150)을 부모 생성자에 고정으로 넘긴다.
    public Warrior(string name) : base(name, 150) { }

    // override: 부모가 허락한(virtual) 메서드를 자식이 덮어씁니다.
    public override void Attack()
    {
        base.Attack(); // 부모의 오리지널 기능(준비 자세)을 먼저 실행
        Console.WriteLine($"[전사] {Name}의 강력한 내려찍기!"); // 덧붙이기
    }
}

public class Mage : GameCharacter
{
    public Mage(string name) : base(name, 80) { }

    public override void Attack()
    {
        base.Attack();
        Console.WriteLine($"[마법사] {Name}의 파이어볼 캐스팅!");
    }
}
```

## 6. Unity 실무에서의 상속

유니티에서 스크립트를 오브젝트에 붙이려면 무조건 `MonoBehaviour`를 상속받아야 합니다. 이미 우리는 상속을 매일 쓰고 있었습니다.

### 6.1 Unity 생명주기(Start, Update)의 함정
콘솔 C#의 생성자는 `base(...)`를 안 적어도 부모 생성자가 불리지만, 유니티의 `Start()`나 `Update()` 같은 유니티 이벤트 함수는 다릅니다.

```csharp
public class Monster : MonoBehaviour
{
    protected virtual void Start() { Debug.Log("몬스터 초기화!"); }
}

public class Orc : Monster
{
    // 여기서 override를 쓰지 않고 냅다 private void Start()를 써버리면,
    // 부모의 Start()는 씹히고 영원히 실행되지 않습니다 (버그의 원인)
    protected override void Start()
    {
        base.Start(); // 반드시 부모의 Start를 명시적으로 불러주어야 합니다
        Debug.Log("오크 도끼 장착");
    }
}
```

### 6.2 상속보다 조합 (Composition over Inheritance)
`Monster ➔ Orc ➔ OrcWarrior ➔ OrcWarriorBoss`\
이렇게 상속이 4단계, 5단계 깊어지면 (Hierarchy Hell), 기획자가 갑자기 **"이 오크 보스는 마법사 스킬도 쓰게 해주세요"** 라고 하는 순간 부모-자식 가계도가 통째로 붕괴됩니다.

**[유니티의 해결책: 컴포넌트(has-a) 패턴]**
* 오크 보스는 `Monster` 클래스가 아닙니다.
* 그냥 텅 빈 `GameObject`에다가 `[체력 컴포넌트]`, `[도끼질 컴포넌트]`, `[마법 컴포넌트]`를 레고 블록처럼 조립해서 갖다 붙이는 방식이 유니티의 핵심 철학입니다
* **상속(is-a)은 동작이 완벽히 갈릴 때만 얇게 쓰고, 나머지는 조립(has-a) 하세요.**

## 7. 실습 문제 및 복습

**Q1. `Animal` 부모 클래스에 매개변수를 받는 생성자만 있습니다. 아래 자식 클래스에서 에러가 나는 이유는?**
```csharp
public class Animal { public Animal(string name) { } }
public class Dog : Animal { public Dog() { } } // 컴파일 에러
```
> **이유**: 자식 객체가 생성될 때 무조건 부모 생성자부터 호출되어야 합니다. C# 컴파일러가 몰래 `Animal`의 기본 생성자 `base()`를 호출하려 했으나, 부모에게는 문자열을 받는 생성자밖에 없어서 짝을 찾지 못해 에러가 발생합니다.\
> **수정**: `public Dog() : base("강아지") { }` 처럼 명시적으로 넘겨주어야 합니다.

**Q2. 어떤 경우에 상속이 부적절한지 `is-a` 관계와 `has-a` 관계를 예로 들어 설명하세요.**
> * **적절 (is-a)**: `Warrior is a Character` (전사는 캐릭터이다). 완벽히 성립하므로 상속(`:`)을 씁니다.
> * **부적절 (has-a)**: `Player is a Weapon` (플레이어는 무기이다). 한국어로 읽어봐도 말이 안 됩니다. 플레이어는 무기를 **'소유(has)'** 하는 관계이므로, 상속이 아니라 클래스 내부에 `Weapon` 타입의 필드(변수)로 가지고 있어야 합니다(조합/컴포지션).

**Q3. `base.Attack()`을 쓰지 않고 자식 클래스에서 `override void Attack()`에 자신만의 기능만 덜렁 적으면 어떻게 되나요?**
> 부모 클래스의 `Attack()` 안에 적어두었던 공통 로직(예: 쿨타임 감소, 마나 소모, 전투 로그 출력 등)이 자식 객체에서는 **아예 실행되지 않고 무시됩니다.** 에러가 나지 않아 발견하기도 힘들며, 자식에서 공통 로직을 처음부터 다시 써야 하는 코드 중복이 발생합니다.

## 8. 주의사항 및 안전 습관

* **부모의 `private` 필드에 억지로 접근하려 하지 마라**: 정 접근해야 한다면 `protected`로 열어주거나, 더 안전하게 부모 쪽에 `protected` 메서드를 만들어서 그 메서드를 통해 값을 바꾸게(캡슐화 유지) 하세요.
* **상속의 깊이는 얕게 (최대 2~3단계)**: 족보가 너무 길어지면 에러가 났을 때 "도대체 이 변수와 함수는 증조할아버지 쪽 건가, 고조할아버지 쪽 건가?" 찾느라 시간을 다 허비하게 됩니다.
* **부모 생성자에 기본값을 모아둬라**: 자식 생성자에서 `public Warrior(string name) : base(name, 150, 20)` 처럼 직업별 고유 수치를 하드코딩해서 부모에게 넘기면, 객체를 생성하는 쪽(Main) 코드가 엄청나게 깔끔해집니다.
