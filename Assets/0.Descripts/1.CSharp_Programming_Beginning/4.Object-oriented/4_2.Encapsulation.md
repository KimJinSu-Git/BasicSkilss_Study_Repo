# [객체 지향] 2. 캡슐화 (Encapsulation)

## 1. 캡슐화란? (Encapsulation)
데이터(필드)와 그 데이터를 다루는 기능(메서드)을 하나의 캡슐처럼 묶고, **데이터 쪽은 외부에서 직접 만지지 못하게 꽁꽁 감추는 객체 지향의 제1원칙**입니다.

> **자판기**
> * 자판기 속의 음료수(데이터)는 유저가 손을 넣어 마음대로 꺼낼 수 없습니다.
> * 정해진 돈을 넣고 **정해진 버튼(메서드/프로퍼티)** 을 눌러야만 정해진 방식으로 음료가 나옵니다.
> * 만약 1,000원을 넣고 `-500원`짜리 음료를 살 수는 없습니다. 자판기의 내부 로직이 잘못된 입력을 알아서 튕겨내며 방어해 주기 때문입니다.

**왜 필요한가?**
```csharp
warrior.hp = 10000;     // 최대 체력이 100인데 10000이 들어간다.
warrior.hp = -100;      // 죽지도 살아 있지도 않은 좀비 상태가 된다.
warrior.level = 9999;   // 경험치 한 번 없이 만렙이 된다.
```
진짜 문제는 값이 이상해진다는 것 자체가 아닙니다. 데이터가 `public`으로 열려 있으면 프로젝트 안의 수천 개 파일 중 **"도대체 누가 언제 이 값을 망가뜨렸는지"** 찾을 수 없어 용의자가 코드 전체가 됩니다.\
캡슐화는 값이 들어오고 나가는 통로를 단 하나(프로퍼티/메서드)로 좁혀서, 버그 추적과 데이터 무결성을 완벽하게 통제하는 일입니다.

## 2. 핵심 요약

| 구분 | 한 줄 설명                                                  |
| :--- |:--------------------------------------------------------|
| **핵심 개념** | **정보 은닉 (Information Hiding)** ➔ 객체의 내부 상태를 외부로부터 꽁꽁 숨김 |
| **최종 목표** | 데이터 무결성 보장 + 값이 바뀌는 통로를 한 곳으로 좁혀서 버그 추적 쉽게 하기           |

| **접근 제한자** | `public` / `protected` / `private` ➔ 어디까지 보여줄지 결정하는 문지기 |

## 3. 세부 개념 및 원리

### 3.1 문제점 ㅡ `public` 필드가 막아 주지 않는 것
```csharp
public class GameCharacter
{
    public int hp;
    public int maxHp;
}
```
이 클래스에는 "체력은 최대 체력을 넘을 수 없다"는 규칙을 적어둘 자리가 없습니다. 쓰는 쪽이 알아서 조심해야 하는 약속으로 남고, 약속은 언젠가 반드시 깨집니다.

필드를 `private`으로 바꾸는 순간, 컴파일러가 규칙을 대신 감시하기 시작합니다.
```csharp
private int hp;
```
`warrior.hp = 10000;` ➔ 이 코드는 이제 컴파일 단계에서 에러를 뿜으며 완벽히 차단됩니다. 실행해 봐야 아는 런타임 버그를 컴파일 오류로 앞당긴 것, 이것이 캡슐화의 첫 번째 이득입니다.

### 3.2 해결책 1 — 접근 제한자 (Access Modifiers)
멤버를 어디까지 보여줄지 고르는 키워드입니다.

| 접근 제한자 | 어디까지 보이는가? | 주로 붙이는 자리 |
| :--- | :--- | :--- |
| **`public`** | 누구나 ➔ 다른 클래스, 다른 파일 어디서든 | 밖으로 공개할 메서드와 프로퍼티 |
| **`protected`** | 자기 자신 + **자식 클래스** | 자식에게만 물려줄 내부 상태 (상속 파트에서 사용) |
| **`private`** | 자기 자신 (오직 같은 클래스 안에서만) | **데이터(필드) 전체**와 내부 전용 메서드 |
> 클래스 멤버에 아무것도 적지 않으면 기본값은 가장 엄격한 `private`이 됩니다.

### 3.3 해결책 2 — 속성 (Property)으로 통제된 통로 만들기
필드를 꽁꽁 감췄으니, 밖에서 안전하게 읽고 쓸 '검문소'가 필요합니다. C#은 **프로퍼티(Property)** 라는 문법을 제공합니다.
```csharp
private int _hp; // 값이 실제로 저장되는 금고 (Backing Field)

// 밖에서 보이는 검문소 (대문자로 시작)
public int Hp 
{
    get { return _hp; }        // 밖에서 값을 읽어갈 때 실행되는 블록
    set { _hp = value; }       // 밖에서 값을 쓸 때 실행되는 블록 (value는 들어온 값)
}
```

`get`과 `set`에 서로 다른 접근 제한자를 붙일 수 있다는 점이 핵심입니다.
```csharp
public int Hp { get; private set; } // 읽기는 누구나 가능, 쓰기는 이 클래스 내부에서만
```

### 3.4 자동 구현 프로퍼티와 `init`
검사할 필요 없이 단순히 읽고 쓰기만 통제할 거라면, 내부 필드(`_hp`)를 굳이 만들 필요 없이 컴파일러에게 맡기면 됩니다.
```csharp
public class GameCharacter
{
    // C#이 보이지 않는 private 필드를 알아서 만들어 줍니다.
    public string Name { get; private set; }
    
    // [C# 9.0+] init 접근자: 태어날 때(생성자) 딱 한 번만 값을 넣을 수 있고,
    // 그 이후엔 내부에서조차 절대 바꿀 수 없는 완벽한 불변(Immutable) 상태로 만듭니다.
    public string PlayerId { get; init; } 
}
```

## 4. 코드로 보는 캡슐화의 위력

### 잘못된 코드 (Before)
```csharp
public class Player
{
    public string name;    // 외부 노출
    public int health;     // 외부 노출
}

Player player = new Player();
player.name = "";      // 이름이 빈 칸이 되는 버그
player.health = -9999; // 체력이 음수가 되는 심각한 버그 (누가 바꿨는지 추적 불가)
```

### 캡슐화된 코드 (After)
```csharp
public class Player
{
    private string _name;
    private int _health;

    public string Name
    {
        get => _name; // '=>' 는 한 줄짜리 return 축약 문법
        set 
        {
            // Fail-fast 원칙: 잘못된 값이 들어오는 순간 조용히 무시하지 않고 예외를 던진다
            if (string.IsNullOrWhiteSpace(value)) 
                throw new ArgumentException("이름은 비어있을 수 없습니다");
            _name = value;
        }
    }

    public int Health
    {
        get => _health;
        set => _health = Math.Clamp(value, 0, 100); // 0 ~ 100 밖의 값은 싹둑 잘라냄
    }
}
```

## 5. 실전 활용 예시 (RPG 전투 시스템)

전사가 슬라임과 싸웁니다. 체력은 0 밑으로 내려가지 않아야 하고, 값이 바뀌는 순간은 오직 피해(TakeDamage)와 회복(Heal)뿐이어야 합니다.

```csharp
public class GameCharacter
{
    public string Name { get; init; }      // 생성 시 한 번 정해지면 절대 안 바뀜
    public int Hp { get; private set; }    // 쓰기는 내부에서만 가능
    public int MaxHp { get; private set; } 

    public bool IsAlive => Hp > 0; // 저장하지 않고 그때그때 계산해서 던져주는 프로퍼티

    public GameCharacter(string name, int maxHp)
    {
        Name = name;
        MaxHp = maxHp;
        Hp = maxHp; // 태어날 땐 풀피
    }

    // 체력을 바꾸는 '유일한 통로 1'
    public void TakeDamage(int damage)
    {
        if (damage <= 0 || !IsAlive) return; // 죽은 자는 말이 없다

        Hp = Math.Max(0, Hp - damage); // 0 아래로 방어
        Console.WriteLine($"  {Name}: {damage} 피해 (HP {Hp}/{MaxHp})");
    }

    // 체력을 바꾸는 '유일한 통로 2'
    public void Heal(int amount)
    {
        if (amount <= 0 || !IsAlive) return; 

        Hp = Math.Min(MaxHp, Hp + amount); // 최대 체력 방어
        Console.WriteLine($"  {Name}: {amount} 회복 (HP {Hp}/{MaxHp})");
    }
}
```
**이 설계의 가치**: 밖에서는 `warrior.Hp = 10000;`을 절대 할 수 없습니다. 체력이 이상해졌다면 버그를 찾을 곳은 오직 `TakeDamage`와 `Heal` 단 두 곳뿐입니다.

## 6. Unity 실무에서의 캡슐화

### 인스펙터 노출과 코드 캡슐화의 완벽한 분리
Unity에서 기획자가 에디터에서 값을 고치게 하려고 필드를 `public`으로 열어버리는 끔찍한 습관이 흔합니다.\
인스펙터 노출과 코드 캡슐화는 철저히 분리해야 합니다.

```csharp
using UnityEngine;

public class PlayerHealth : MonoBehaviour
{
    // [SerializeField]: 코드는 private으로 철통 방어하면서, Unity 인스펙터 창에는 예쁘게 띄워줍니다
    [SerializeField] private int _maxHealth = 100;
    private int _currentHealth;

    // 다른 스크립트(UI, 몬스터 등)는 오직 읽기(get)만 가능합니다.
    public int CurrentHealth => _currentHealth;

    void Start()
    {
        _currentHealth = _maxHealth;
    }

    // 외부에서 체력을 깎고 싶다면 프로퍼티가 아니라 반드시 '명확한 의도가 담긴 메서드'를 호출하게 강제합니다.
    public void TakeDamage(int amount)
    {
        _currentHealth = Mathf.Clamp(_currentHealth - amount, 0, _maxHealth);
    }
}
```

## 7. 실습 문제 및 복습

**Q1. `public int Level { get; set; }` 과 `public int Level { get; private set; }` 의 치명적 차이는?**
> * `{ get; set; }` : 외부에서 누구나 마음대로 `player.Level = 9999;` 로 쑤셔 넣을 수 있어 위험합니다.
> * `{ get; private set; }` : 외부에서는 `player.Level`로 읽기만 가능하고, 레벨을 올리는 작업은 오직 클래스 내부의 `LevelUp()` 같은 안전한 메서드를 통해서만 이루어지도록 강제합니다.

**Q2. "모든 필드에 무조건 `{ get; set; }`을 붙이는 것이 캡슐화의 정석이다"라는 주장이 틀린 이유는?**
> 아무런 검증 로직 없이 냅다 `{ get; set; }`만 열어두는 것은 `public` 필드와 완전히 똑같습니다. 캡슐화의 진정한 목적은 통로를 만드는 것 자체가 아니라, **외부에서 조작할 필요가 없는 데이터를 철저히 닫아버리고(`private set`), 조작이 필요한 곳에는 반드시 검증 로직(Validation)을 통과하게 만드는 것**입니다.

**Q3. 캐릭터가 독에 걸려 매 턴 체력이 5씩 깎여야 합니다. 이를 외부 클래스에서 `character.Hp -= 5;`로 짜면 안 되는 이유와 올바른 설계는?**
> 외부에서 체력을 직접 깎으면, 체력이 0 밑으로 떨어지지 않게 막아주는 방어 로직과 사망 시 애니메이션을 재생하는 로직 등을 외부 클래스에서 똑같이 또 짜야 합니다(코드 중복).
> 올바른 설계는 외부에서는 "독 데미지 5를 입어라!"라고 `character.TakeDamage(5);` 메서드(기존에 만들어둔 안전한 통로)를 호출해 주기만 하는 것입니다.

## 8. 주의사항 및 안전 습관

* **가장 좁게 열고 필요할 때 넓혀라**: 처음에는 무조건 모든 필드와 메서드를 `private`으로 둡니다. 외부에서 진짜 필요하다고 할 때만 하나씩 `public` (또는 `private set`)으로 열어주세요.
* **`set` 안에서 무한 루프 폭발 주의**:
  ```csharp
  public int Hp { get => Hp; set => Hp = value; } // 스택 오버플로 폭발
  ```
  프로퍼티의 `set` 안에서 자기 자신(`Hp`)에 값을 넣으려 하면 무한 호출에 빠집니다. 반드시 숨겨진 진짜 필드(`_hp`)에 값을 넣어야 합니다.
* **프로퍼티 안에서 무거운 연산 금지**: 프로퍼티는 생긴 게 변수라서 밖에서 반복문 안에서 가볍게 읽어다 씁니다. 프로퍼티 안쪽에 파일을 읽거나 무거운 수학 계산을 넣으면 엄청난 렉이 걸립니다. 무거운 작업은 반드시 메서드(`GetHpFromDB()`)로 만드세요.
