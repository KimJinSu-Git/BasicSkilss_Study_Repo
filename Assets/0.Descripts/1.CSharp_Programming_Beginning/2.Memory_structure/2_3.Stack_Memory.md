# [메모리와 구조] 3. 스택 메모리 (Stack Memory)

## 1. 스택 메모리란?
스택(Stack) 메모리는 프로그램이 실행될 때 "지금 내가 무슨 일을 어떤 순서로 하고 있는지"를 기억하는 매우 빠르고 체계적인 **단기 작업 기억 공간**입니다.

메서드가 호출될 때마다 작업 공간(스택 프레임)이 차곡차곡 쌓이고, 임무를 다하면 가장 위에 있는 것부터 즉시 제거되는 **후입선출(LIFO, Last-In First-Out)** 구조를 가집니다.

> **책상 위에 포스트잇 겹쳐 붙이기**
> * **메서드 호출 (`Push`)** : 일하던 중간에 급한 요청이 오면, 원래 보던 서류 위에 새 포스트잇을 덧붙임
> * **메서드 종료 (`Pop`)** : 방금 끝낸 맨 위 포스트잇을 떼어내 쓰레기통에 버리고, 바로 아래에 있던 원래 작업으로 자연스럽게 돌아감

**왜 필요한가?**\
스택이 없다면 프로그램은 메서드를 호출한 뒤 "방금 어디까지 일하고 있었지?" 하며 길을 잃습니다. 스택은 함수 호출의 작업 순서를 추적하고, 메서드 안에서 잠깐 쓰고 버릴 **지역 변수들을 위한 임시 저장 공간을 매우 빠르게 제공**합니다.

## 2. 핵심 요약

| 특징 | 한 줄 설명                                            |
| :--- |:--------------------------------------------------|
| **구조** | **LIFO** (후입선출) ➔ 가장 마지막에 들어온 데이터가 가장 먼저 나감       |
| **속도** | **극강의 속도** ➔ 포인터만 위아래로 옮기므로 메모리 할당/해제 오버헤드가 0에 수렴 |
| **관리 주체** | OS / .NET 런타임 ➔ 자동 관리 (가비지 컬렉터도 개입하지 않음)          |
| **저장 데이터** | 메서드 매개변수, 지역 변수(값 타입의 알맹이 또는 참조 타입의 주소), 복귀 주소    |
| **스택 프레임** | 메서드가 한 번 호출될 때마다 만들어지는 그 메서드만의 **독립된 작업 방**       |
| **크기** | 스레드마다 고정된 아주 작은 크기 (보통 **1MB**)                   |
| **초과 시** | `StackOverflowException` (프로그램 즉시 강제 종료)          |

## 3. 세부 개념 및 실무 원리

### 3.1 스택 프레임 (Stack Frame) : 메서드별 독립된 방
메서드가 호출될 때마다 통째로 하나씩 쌓이는(Push) 논리적인 블록입니다. 프레임 안에는 다음 내용이 들어갑니다.
1. **매개변수**: 넘어온 인자의 복사본
2. **지역 변수**: 메서드 중괄호 `{ }` 안에서 선언된 변수들
    * 값 타입(`int`, `bool`, `struct`): **데이터 본체**가 스택에 직접 저장됨
    * 참조 타입(`class`, 배열): 본체는 힙(Heap)에 저장하고, 스택에는 **힙을 가리키는 주소(리모컨)** 만 저장됨
3. **복귀 주소**: 이 메서드가 끝나면 되돌아갈 원래 코드의 위치

메서드가 종료되면 이 방 전체가 통째로 제거(Pop)되며, 방 안에 있던 지역 변수도 함께 소멸합니다.

### 3.2 스택 메모리는 왜 그렇게 미친 듯이 빠를까?
스택은 '스택 포인터(Stack Pointer)'라는 단 하나의 줄자 눈금만 관리합니다.
* **할당(`Push`)**: 눈금을 위로 살짝 옮기고 거기에 데이터를 씁니다.
* **해제(`Pop`)**: 눈금을 아래로 다시 내리기만 합니다. (실제로 데이터를 지울 필요도 없이, 다음 번에 그냥 덮어씁니다.)

힙(Heap)처럼 '어디에 빈 공간이 있나' 탐색할 필요도 없고, 파편화도 없으며, 가비지 컬렉터(GC)를 부를 필요도 없기 때문에 CPU 캐시 친화적이고 극도로 빠릅니다.

### 3.3 배열을 1만 개 만들면 스택이 터질까?
`int[] arr = new int[10000];`을 메서드 안에서 선언한다고 가정합시다. 스택 크기가 1MB밖에 안 되는데 터질까요?\
➔ **정답은 "안 터진다" 입니다.**\
배열은 **참조 타입(`class`)** 이므로 거대한 1만 칸짜리 본체는 넉넉한 힙(Heap) 메모리에 지어지고, 비좁은 스택에는 8바이트짜리 **주소(참조)값 하나**만 달랑 올라가기 때문에 안전합니다.

## 4. 코드로 보는 스택 메모리의 흐름

### 4.1 호출과 복귀 (디버깅의 꽃, 호출 스택)
메서드가 차례로 호출되면서 프레임이 쌓였다가 걷히는 모습입니다. 들여쓰기 깊이가 곧 지금 스택에 쌓여 있는 프레임의 개수입니다.

```csharp
public static void Main()
{
    int a = 10; // 1) Main 프레임 (스택 가장 아래)
    Console.WriteLine($"[1] Main 시작 — a = {a}");
    
    FirstMethod(); // 2) First 프레임 Push
    
    Console.WriteLine($"[6] Main 종료 — a = {a}");
} // 7) Main 프레임 Pop (프로그램 종료)

public static void FirstMethod()
{
    int b = 20; // 3) First 프레임의 지역 변수
    Console.WriteLine($"  [2] First 시작 — b = {b}");
    
    SecondMethod(); // 4) Second 프레임 Push
    
    Console.WriteLine($"  [5] First 종료 — b = {b}");
} // 6) First 프레임 Pop (b 소멸)

public static void SecondMethod()
{
    int c = 30; // 4-1) Second 프레임의 지역 변수
    Console.WriteLine($"    [3] Second 시작 — c = {c}");
    Console.WriteLine($"    [4] Second 종료 — c = {c}");
} // 4-2) Second 프레임 Pop (c 소멸)
```
> **핵심 원리**
> 1. **가장 안쪽에서 시작한 일이 가장 먼저 끝납니다.** `SecondMethod`가 마지막으로 불렸지만 가장 먼저 종료됩니다 (LIFO).
> 2. **프레임끼리는 서로의 변수를 볼 수 없습니다.** `SecondMethod` 안에서 `FirstMethod`의 변수 `b`를 찾으면 에러가 납니다. 각각 철저히 독립된 방이기 때문입니다.

### 4.2 StackOverflowException
```csharp
// ❌ 잘못된 코드: 종료 조건 누락
static void RecursiveCall(int n)
{
    Console.WriteLine($"호출 깊이: {n}");
    RecursiveCall(n + 1); // 영원히 빠져나올 수 없는 굴레
}

// ⭕ 올바른 코드: 탈출구(종료 조건)가 필수
static int Factorial(int n)
{
    // 재귀 함수의 첫 줄은 무조건 종료 조건이어야 합니다.
    if (n <= 1) return 1; 
    
    return n * Factorial(n - 1);
}
```
> 스택 메모리(1MB)는 방이 아주 좁습니다. `RecursiveCall(0);`을 부르면 1MB를 꽉 채울 때까지 프레임이 수만 번 쌓이다가, 결국 **`StackOverflowException`** 을 뱉으며 게임(프로그램)이 즉시 강제 종료됩니다.

## 5. Unity에서의 스택 메모리 활용 

```csharp
using UnityEngine;

public class Player : MonoBehaviour
{
    // 힙(Heap) 영역: 이 클래스의 객체 본체는 힙에 존재하므로, 
    // health 필드도 객체가 살아있는 내내 힙 메모리에 상주합니다.
    public int health = 100;
    public Vector3 velocity;

    void Update()
    {
        // 스택(Stack) 영역: 매 프레임마다 Update 프레임 방이 새로 생깁니다.
        float deltaTime = Time.deltaTime;     
        Vector3 movement = velocity * deltaTime; // Vector3는 struct이므로 스택에 올라감

        transform.position += movement;
        
        // 🗑Update 종료 시 프레임 Pop
        // 지역 변수인 deltaTime과 movement는 깔끔하게 흔적도 없이 사라집니다.
    }
}
```

> **[디버깅 팁]** Visual Studio나 Rider에서 오류가 났을 때 우측 하단에 뜨는 **호출 스택 (Call Stack)** 창이 바로 이 스택 메모리의 현재 상태를 보여주는 패널입니다. 에러가 나기 직전까지 "어떤 메서드를 타고 들어왔는지" 역추적할 수 있는 가장 강력한 디버깅 도구입니다.

## 6. 실습 문제 및 복습

**Q1. LIFO는 무엇의 약자이고, 어떤 특징을 가지나요?**
> **Last-In, First-Out (후입선출)**. 가장 나중에 들어간 데이터(메서드 프레임)가 가장 먼저 빠져나오는 구조입니다. 책상 위에 책을 쌓았다가 맨 위부터 빼내는 방식과 동일합니다.

**Q2. 왜 C#은 메모리를 굳이 스택(Stack)과 힙(Heap)으로 나누어 쓸까요?**
> **각자의 장점이 뚜렷하기 때문입니다.**
> * **스택(Stack)**: 관리가 자동이고 속도가 미친 듯이 빠릅니다. 하지만 크기가 작고 수명이 짧습니다. ➔ 잠깐 쓰고 버릴 계산용 지역 변수들에 적합
> * **힙(Heap)**: 할당 속도가 느리고 수동 관리(GC)가 필요하지만, 용량이 엄청나게 크고 수명이 깁니다. ➔ 오랫동안 기억해야 하는 무거운 객체(몬스터 데이터, 텍스처 등)에 적합

**Q3. 아래 코드에서 변수 `player`, 매개변수 `name`, 실제 `"Knight"` 문자열 데이터는 각각 스택과 힙 중 어디에 존재하나요?**
```csharp
public class Player { public string Name; }

void Main() {
    Player player = new Player();
    ChangeName(player, "Knight");
}
void ChangeName(Player p, string name) {
    p.Name = name;
}
```
> * `player` 변수: **스택** (Main 프레임의 지역 변수)
> * `new Player()`로 만들어진 객체 본체: **힙**
> * 매개변수 `name` 변수: **스택** (ChangeName 프레임의 지역 변수)
> * `"Knight"`라는 실제 문자열 데이터: **힙** (string은 참조 타입이므로)

## 7. 주의사항 및 안전 습관

* **재귀 함수의 첫 줄은 언제나 탈출구(종료 조건)로 시작하라**: 조건을 깜빡하면 에디터가 통째로 멈춰버립니다.
* **지나치게 깊은 호출 체인을 피해라**: A가 B를 부르고, B가 C를 부르고... 꼬리에 꼬리를 무는 스파게티 코드는 스택 추적(디버깅)을 지옥으로 만듭니다.
* **거대한 `struct`를 지역 변수로 남발하지 마라**: 구조체는 값 타입이므로 스택에 뚱뚱한 데이터가 통째로 올라가게 됩니다. `struct`는 작고 가볍게 설계하는 것이 원칙입니다.
