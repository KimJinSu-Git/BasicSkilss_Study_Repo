# [메모리와 구조] 7. 열거형 (enum)

## 1. 열거형(Enum)이란?
열거형(Enumeration)은 서로 관련 있는 '정수 상수'들의 묶음에 타입 이름을 부여하고, 그 안의 값마다 사람이 읽기 쉬운 '이름표'를 붙인 문법입니다.

> **창고 관리 대장**\
> 창고에 상자가 다섯 개 있고, 관리 대장에는 번호만 적혀 있습니다. "3번 상자 가져와!"\
> 번호를 외운 고인물(?)에게는 문제가 없지만, 신입은 3번이 뭔지 모릅니다. 게다가 대장에 실수로 "99번 상자"라고 적어도 창고 관리 시스템은 경고해주지 않습니다.\
> 상자마다 "회복약", "폭탄"이라는 **이름표를 붙이고 대장에도 이름으로 적게 강제하는 것**, 그것이 바로 열거형입니다.

**왜 필요한가?**\
캐릭터의 상태를 정수(`0`: 대기, `1`: 걷기, `2`: 공격)로 관리하면 당장은 코드가 돌아갑니다. 하지만,
1. **읽을 수 없습니다**: `if (state == 2)` 만 보고는 공격인지 방어인지 알 수 없습니다.
2. **아무 값이나 들어갑니다**: `state = 99;` 라는 존재하지 않는 엉뚱한 값을 넣어도 컴파일러가 잡아내지 못합니다.
3. **뜻이 흩어집니다**: "2는 공격"이라는 약속이 프로그래머의 머릿속에만 존재하다가, 팀원이 바뀌면 그 뜻도 사라집니다.

열거형은 이 약속들을 묶어 **새로운 타입(Type)으로 승격**시킵니다. 약속이 타입이 되면, 그 뒤로는 C# 컴파일러가 약속을 지켜줍니다.

## 2. 핵심 요약

| 특징 | 한 줄 설명 |
| :--- | :--- |
| **개념** | 이름표가 붙은 정수 상수들의 묶음이자, 그 자체로 독립적인 타입 |
| **메모리** | **값 타입 (Value Type)**. 기본적으로 `int`(4바이트)를 기반으로 작동함 |
| **기본값** | 값을 명시하지 않으면 위에서부터 차례대로 `0, 1, 2...`가 부여됨 |
| **형 변환** | 명시적 캐스팅(`(int)`)으로 정수와 양방향 변환 가능 |
| **순서와 비교** | 기반 정수끼리 크기를 비교(`>`)할 수 있으므로, 나열 순서가 곧 서열(의미)이 됨 |
| **다중 선택** | `[Flags]` 속성을 붙이고 비트 연산을 사용해 한 변수에 여러 상태를 담을 수 있음 |

## 3. 세부 개념 및 원리

### 3.1 정의 : 이름을 나열하면 끝입니다.
```csharp
// 아이템 등급 (기본적으로 int 기반)
public enum ItemRarity
{
    Common,     // 0
    Uncommon,   // 1
    Rare,       // 2
    Epic,       // 3
    Legendary   // 4
}
```

만약 저장 파일이나 서버 코드 호환을 위해 특정 번호가 필요하다면 값을 직접 못 박을 수도 있습니다.
```csharp
// 네트워크 크기 최적화를 위해 기반 타입을 byte(1바이트)로 변경
public enum Direction : byte
{
    Up = 10,
    Down = 20,
    Left = 30,
    Right // 값을 안 주면 위에서 +1 된 31이 됨
}
```

### 3.2 정수와의 양방향 변환 (주의: 컴파일러는 검사하지 않는다)
열거형과 정수는 명시적 캐스트(`(int)`)로 오갈 수 있습니다.
```csharp
int num = (int)ItemRarity.Epic;   // 3 (열거형 ➔ 정수)
ItemRarity rarity = (ItemRarity)2; // Rare (정수 ➔ 열거형)
```

**[치명적인 함정]**\
캐스트는 그 값이 실제로 열거형에 정의되어 있는지 확인하지 않습니다.
```csharp
ItemRarity broken = (ItemRarity)99; // 컴파일 에러도, 런타임 에러도 안 납니다
Console.WriteLine(broken);          // "99" (이름이 없으니 그냥 숫자 출력)
```
**해결책**: 세이브 파일이나 서버 등 '외부'에서 들어온 정수를 열거형으로 바꿀 때는 무조건 방어 코드를 짜야 합니다.
```csharp
int savedValue = 99;

// Enum.IsDefined 로 정의된 값인지 검사
if (Enum.IsDefined(typeof(ItemRarity), savedValue))
    rarity = (ItemRarity)savedValue;
else
    rarity = ItemRarity.Common; // 알 수 없는 값이면 기본값으로 떨어뜨림 (안전빵)
```

### 3.3 여러 개를 한 변수에 담기 : `[Flags]`와 비트 연산 
상태 이상(독, 화상, 기절)처럼 동시에 여러 개가 걸릴 수 있는 상태는 `[Flags]` 속성과 **비트 연산**을 조합합니다.\
값은 반드시 **2의 거듭제곱**(`1, 2, 4, 8...`)으로 배정해야 비트가 겹치지 않습니다.

```csharp
[Flags]
public enum StatusEffect
{
    None   = 0,        // 0000 (아무 상태 아님. 필수!)
    Poison = 1 << 0,   // 0001 (1)
    Slow   = 1 << 1,   // 0010 (2)
    Stun   = 1 << 2,   // 0100 (4)
    Burn   = 1 << 3    // 1000 (8)
}

// 상태 추가 (OR 연산자 '|')
StatusEffect myStatus = StatusEffect.Poison | StatusEffect.Slow;

// 상태 검사 (HasFlag 메서드 활용)
if (myStatus.HasFlag(StatusEffect.Poison)) Console.WriteLine("독에 걸렸습니다");

// 상태 제거 (AND & NOT 연산자 조합)
myStatus &= ~StatusEffect.Slow; // 둔화만 쏙 빼냄
```

## 4. 코드로 보는 `enum`의 위력 (Before & After)

### Before: 매직 넘버(Magic Number)의 늪
```csharp
int rarity = 2;

// 반년 뒤에 이 코드를 보면 '3'이 무슨 등급인지 절대 기억 못 함
if (rarity >= 3)
    Console.WriteLine("영웅 등급 이상입니다.");

rarity = 99; // 버그 발생 : 존재하지 않는 등급
int playerLevel = 7;
rarity = playerLevel; // 끔찍한 버그 : 레벨이 등급에 대입됨
```

### After: 열거형으로 완성된 타입 세이프티(Type Safety)
```csharp
ItemRarity rarity = ItemRarity.Rare;

// 이 줄만 봐도 코드가 영어 문장처럼 술술 읽힘
if (rarity >= ItemRarity.Epic)
    Console.WriteLine("영웅 등급 이상입니다.");

// rarity = 99; // ❌ 컴파일 에러 정수 대입 불가
// rarity = playerLevel; // ❌ 컴파일 에러 타입 다름
```

## 5. 실전 활용 예시 (아이템 시스템) 

`switch` 문과 결합하면 완벽한 분기 처리가 가능합니다. 여기서 **`default`는 선택이 아닌 필수**입니다 (정의되지 않은 쓰레기 값이 들어왔을 때를 대비한 방패)

```csharp
public string GetRarityName(ItemRarity rarity)
{
    switch (rarity)
    {
        case ItemRarity.Common:    return "일반";
        case ItemRarity.Uncommon:  return "고급";
        case ItemRarity.Rare:      return "희귀";
        case ItemRarity.Epic:      return "영웅";
        case ItemRarity.Legendary: return "전설";
        default:                   
            return "알 수 없는 아이템"; // 방어 코드
    }
}
```

## 6. Unity 최적화 및 꿀팁

### 6.1 인스펙터의 드롭다운
`[SerializeField] private ItemRarity rarity;`\
위처럼 선언하면 유니티 인스펙터에 멋진 드롭다운 박스가 생깁니다. 기획자가 숫자를 외울 필요 없이 클릭으로 등급을 정할 수 있어 휴먼 에러가 원천 차단됩니다.

### 6.2 [주의] `enum`의 순서를 중간에 바꾸지 마라!
유니티 인스펙터와 씬 파일(Prefab)은 열거형의 이름(`Rare`)이 아니라 **기반 정수(`2`)** 를 저장합니다.\
만약 `Uncommon`과 `Rare` 사이에 `Advanced`라는 등급을 새로 끼워 넣으면 어떻게 될까요?\
원래 `2`였던 `Rare`가 `3`으로 밀려나고, 기존 프리팹에 `2`로 저장되어 있던 전설의 검들은 전부 `Advanced` 등급으로 강등되는 대참사가 발생합니다.
> **원칙**: 새로운 `enum` 멤버는 **무조건 맨 밑에 추가**하거나, 처음부터 `Common = 0, Uncommon = 1` 처럼 **값을 명시적으로 고정**해 두어야 합니다.

### 6.3 언제 FSM(유한 상태 기계)으로 넘어가야 할까?
플레이어 상태를 `enum`으로 만들고 `switch`로 돌리는 것은 훌륭한 시작입니다.\
하지만 "점프 중에는 공격 모션 재생 불가", "맞고 있으면 구르기 불가" 등 상태 간의 간섭과 예외 처리로 인해 `switch`문이 수백 줄을 넘어가며 꼬이기 시작한다면?\
그때가 바로 열거형을 버리고, 상태 자체를 클래스로 떼어내는 **상태 패턴(State Pattern / FSM)** 아키텍처로 진화해야 할 시점입니다.

## 7. 실습 문제 및 복습

**Q1. `ItemRarity broken = (ItemRarity)99;` 코드가 에러 없이 통과하는 이유는 무엇이고, 방어 방법은?**
> C#의 명시적 캐스팅은 런타임 성능을 위해 값이 `enum`에 정의되어 있는지 검사하지 않습니다. 세이브 파일 등 외부에서 값을 받아올 때는 반드시 `Enum.IsDefined(typeof(ItemRarity), 99)`를 사용해 방어 코드를 짜야 합니다.

**Q2. `[Flags]` 속성을 사용할 때 멤버의 값을 `0, 1, 2, 3`이 아니라 `1, 2, 4, 8`로 지정하는 이유는?**
> 상태들을 한 변수에 비트 연산(`|`, `&`)으로 조합하기 위함입니다. 2의 거듭제곱으로 값을 할당해야 2진수로 변환했을 때 각 상태가 독립적인 자릿수를 차지하여 겹치지 않고 온전하게 데이터를 보존 및 추출할 수 있습니다.

**Q3. `enum`의 이름 문자열을 그대로 사용하는 `ToString()`이나 `Enum.TryParse()`를 `Update()` 문에서 매 프레임 사용하면 안 되는 이유는? (성능 관점)**
> 이 메서드들은 내부적으로 리플렉션(Reflection) 연산과 문자열 객체의 힙 할당, 즉 **박싱(Boxing)** 을 유발합니다. 매 프레임 호출하면 가비지 컬렉터(GC)에 엄청난 쓰레기를 던져주어 프레임 드랍(스파이크)을 일으킵니다. 문자열 파싱은 로딩이나 세이브 시점에 단 한 번만 수행해야 합니다.

## 8. 주의사항 및 안전 습관

* **0번 자리(기본값)를 신중하게 정하라**: `int` 기반의 열거형은 초기화하지 않으면 무조건 `0`으로 시작합니다. `0` 자리에 `None`, `Idle`, `Unknown` 같이 "아무 상태도 아님"을 의미하는 기본값을 두는 것이 가장 안전한 설계입니다.
* **비교 연산자(`>`, `<`)는 순서에 의미가 있을 때만**: 등급(`Epic > Rare`)에는 의미가 있지만, 직업(`Warrior > Mage`)은 아무 의미가 없습니다. 순서가 없는 단순 분류는 `==` 나 `!=` 로만 비교하세요.
* **문자열은 경계에서만 다뤄라**: 서버에서 온 JSON 등에서 문자열(`"Rare"`)을 받으면, 통신 경계선에서 즉시 `Enum.TryParse`로 `enum` 타입으로 변환하세요. 핵심 게임 로직 내부로 문자열 변수를 끌고 들어와 `== "Rare"` 처럼 비교하는 짓은 최악의 성능을 냅니다.
