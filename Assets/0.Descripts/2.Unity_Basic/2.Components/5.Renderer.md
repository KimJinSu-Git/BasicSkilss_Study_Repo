# [Components] 5. Renderer (렌더러)

## 1. Renderer 란?
> **'무대의 조명과 의상 담당'**
> * **`Mesh` (메시)** : 배우의 뼈대와 골격 — "어떤 체형(모양)인가?"
> * **`Material` (머티리얼)** : 의상과 분장 — "어떤 색깔과 재질(질감)의 옷을 입었는가?"
> * **`Renderer` (렌더러)** : 배우를 무대에 세우고 조명을 비춰 관객에게 보여주는 담당자 — "실제로 화면에 보이게 출력하는 사람"

**왜 필요한가?**\
`GameObject`에 `Transform`으로 위치를 잡아주고 `Mesh Filter`로 뼈대를 붙여도, 그것을 GPU에 넘겨 "모니터에 그려라"라고 지시하는 `Renderer` 컴포넌트가 없으면 게임 화면에는 아무것도 나타나지 않습니다.\
역할이 이렇게 분리된 덕분에, 오브젝트를 잠깐 숨길 때 `GameObject`를 끄지 않고 `Renderer`만 꺼버리거나, 똑같은 몬스터의 색깔만 바꿀 때 뼈대(Mesh)는 냅두고 옷(Material)만 갈아입히는 최적화가 가능해집니다.

---

## 2. 핵심 요약

| 개념 | 한 줄 설명 |
| :--- | :--- |
| **Renderer** | 모든 렌더링 컴포넌트의 공통 조상 (부모 클래스) |
| **Mesh Renderer** | `Mesh Filter`와 한 쌍으로 움직이며 3D 오브젝트(배경, 아이템)를 그림 |
| **Skinned Mesh Renderer**| 뼈대(Bone)와 애니메이션이 있는 3D 캐릭터(플레이어, 몬스터)를 그림 |
| **Sprite Renderer** | 2D 이미지(스프라이트)를 그림 |
| **Tilemap Renderer** | 2D 격자 타일 수천 개를 하나의 덩어리로 압축(배칭)해서 한 번에 그림 |
| **Particle System Renderer**| 수천 개의 파티클(이펙트) 입자를 한 번에 그림 |

> **[원칙]**
> 1. `Renderer` 컴포넌트 하나는 곧 렌더링 비용(Draw Call) 1개를 의미합니다. 적을수록 좋습니다.
> 2. 코드로 색상을 바꿀 때 `renderer.material`을 쓰면 사본이 복제되어 메모리가 터집니다. 반드시 **`MaterialPropertyBlock`** 을 쓰거나, 2D는 `spriteRenderer.color`를 써야 합니다.
> 3. 무언가 안 보일 때는 `gameObject.SetActive(false)` 보다 **`renderer.enabled = false`** 로 그리기만 끄는 것이 생명주기 꼬임을 막는 최고의 습관입니다.

## 3. 세부 개념 및 원리

### 3.1 `Mesh Renderer` (일반 3D 오브젝트)
집, 바위, 무기 등 모양이 고정된 3D 모델을 그립니다. 혼자서는 뼈대를 알 수 없어 항상 **`Mesh Filter`** 컴포넌트와 짝꿍으로 다닙니다.

| 인스펙터 주요 항목 | 하는 일 |
| :--- | :--- |
| **Materials** | 입혀줄 옷(머티리얼) 목록. 부위별로 다르면 슬롯도 여러 개가 됩니다. |
| **Cast Shadows** | 이 오브젝트가 바닥에 그림자를 드리울지 여부 (On, Off, Two Sided 등) |
| **Receive Shadows** | 다른 오브젝트의 그림자가 내 몸에 맺힐지 여부 |

### 3.2 `Skinned Mesh Renderer` (움직이는 3D 캐릭터)
관절(Bone) 애니메이션이 적용되어 매 프레임 모양이 구겨지고 바뀌는 3D 캐릭터에 씁니다.\
모양이 계속 바뀌므로 `Mesh Filter` 없이 자기 자신이 직접 뼈대 정보(`Root Bone`)와 변형되는 메시를 짊어지고 다닙니다.
* **성능 팁**: 팔다리가 화면 밖으로 나가도 캐릭터가 안 사라지게 하려면, 컬링(화면 밖 지우기)의 기준이 되는 **`Bounds`(경계 상자)** 값을 넉넉하게 잘 잡아주어야 합니다.

### 3.3 `Sprite Renderer` (2D 그래픽)
2D 게임의 모든 것입니다. 3D와 달리 복잡한 빛 계산이나 머티리얼 조작 없이, 인스펙터의 **`Color`** 속성 하나로 피격 시 빨갛게 변하는 등의 처리가 가능해 매우 편합니다. 정렬 순서는 `Sorting Layer`와 `Order in Layer`로 완벽히 통제됩니다.

### 3.4 궤적을 그리는 `Line`과 `Trail` Renderer
* **`Line Renderer`**: 코드로 점(Point) 좌표들을 연결해 레이저 포인터나 포물선 궤적을 그립니다.
* **`Trail Renderer`**: 총알이나 칼끝에 달아두면, 오브젝트가 이동한 궤적(잔상)을 자동으로 예쁘게 남겨줍니다.

## 4. 코드로 보기 (피격 시 깜빡임 연출)

몬스터가 맞았을 때 잠깐 하얗게 빛나는 연출입니다. 메모리를 터뜨리는 최악의 코드와, 한 줌의 메모리 누수도 없는 정석 코드의 비교입니다.

### 잘못된 방법 (머티리얼 복제 참사)
~~~csharp
public class BadHitFlash : MonoBehaviour
{
    private Renderer _rend;
    private void Awake() => _rend = GetComponent<Renderer>();

    public void Flash()
    {
        // 실수: .material 에 접근하는 순간 유니티는 원본을 훼손하지 않기 위해 
        // 몬스터 전용 '머티리얼 복사본(Instance)'을 몰래 찍어냅니다. 
        // 몬스터 100마리가 맞으면 머티리얼도 100개가 생겨 드로우콜이 터지고 배칭이 박살납니다
        _rend.material.color = Color.white; 
    }
}
~~~
> **참고**: 반대로 `.sharedMaterial`을 쓰면 메모리 복제는 안 일어나지만, 프로젝트 폴더 안의 **원본 에셋 파일 자체 색상이 하얗게 바뀌어버려서** 씬에 있는 모든 몬스터가 다 같이 하얗게 변하는 대참사가 일어납니다.

### 정석 방법 (MaterialPropertyBlock 활용)
~~~csharp
public class GoodHitFlash : MonoBehaviour
{
    // URP Lit 셰이더의 기본 색상 프로퍼티 ID (미리 캐싱하여 성능 극대화)
    private static readonly int BaseColorId = Shader.PropertyToID("_BaseColor");

    private Renderer _rend;
    private MaterialPropertyBlock _propBlock; // 머티리얼을 복제하지 않고 값만 덧씌우는 투명 필름지

    private void Awake()
    {
        _rend = GetComponent<Renderer>();
        _propBlock = new MaterialPropertyBlock();
    }

    public void Flash(Color flashColor)
    {
        // 1. 현재 렌더러의 프로퍼티 상태를 투명 필름지(Block)에 복사해옴
        _rend.GetPropertyBlock(_propBlock); 
        
        // 2. 필름지의 색상만 변경
        _propBlock.SetColor(BaseColorId, flashColor);
        
        // 3. 필름지를 다시 렌더러에 덮어씌움 (메모리 복제 발생 X)
        _rend.SetPropertyBlock(_propBlock);
    }
}
~~~

## 5. 실전 활용 예시: 사망 페이드 아웃 연출

보스가 죽었을 때 연기처럼 서서히 투명해지며(Fade-Out) 사라지는 공용 시각 연출 스크립트입니다.\
몸통, 무기, 날개 등 여러 개의 렌더러를 한 번에 처리합니다.

~~~csharp
using System.Collections;
using UnityEngine;

public class EnemyVisual : MonoBehaviour
{
    [SerializeField] private float _fadeTime = 1f;
    [SerializeField] private Color _baseColor = Color.white; 
    private static readonly int BaseColorId = Shader.PropertyToID("_BaseColor");

    private Renderer[] _renderers; // 몸통, 무기 등 자식 렌더러까지 전부 모을 배열
    private MaterialPropertyBlock _block;

    private void Awake()
    {
        // GetComponentsInChildren은 무거우므로 반드시 Awake에서 1번만
        _renderers = GetComponentsInChildren<Renderer>();
        _block = new MaterialPropertyBlock();
    }

    public void PlayDeathFade() => StartCoroutine(FadeOutRoutine());

    private IEnumerator FadeOutRoutine()
    {
        float elapsed = 0f;
        while (elapsed < _fadeTime)
        {
            elapsed += Time.deltaTime;
            float alpha = 1f - (elapsed / _fadeTime); // 1에서 0으로 서서히 깎임
            
            SetColorToAll(new Color(_baseColor.r, _baseColor.g, _baseColor.b, alpha));
            yield return null;
        }

        // 투명해졌으면 오브젝트를 파괴하지 않고 깔끔하게 렌더러만 꺼준다 (오브젝트 풀링 대비)
        foreach (var r in _renderers) r.enabled = false;
    }

    private void SetColorToAll(Color color)
    {
        foreach (Renderer r in _renderers)
        {
            r.GetPropertyBlock(_block);
            _block.SetColor(BaseColorId, color);
            r.SetPropertyBlock(_block);
        }
    }
}
~~~
* **주의사항**: 3D 모델의 알파(투명도)를 내렸는데도 안 투명해진다면, 머티리얼의 셰이더 설정(`Surface Type`)이 **Opaque(불투명)** 로 되어 있기 때문입니다. 페이드 아웃을 하려면 반드시 **Transparent(반투명)** 로 설정되어 있어야 합니다.

## 6. Unity 최적화 팁

### 6.1 칸 9,000개를 그리는 최적화의 마법 (`Tilemap Renderer`)
타일 기반 2D 농장 게임에서 96x96 사이즈(9,216칸)의 거대한 맵을 만들 때, 타일마다 `GameObject`와 `Sprite Renderer`를 9,216개 만들어 배치하면 모바일 게임은 프레임이 터져버립니다 (Draw Call 지옥).\
과거 프로그래머들은 이를 해결하기 위해 직접 32x32 청크(Chunk) 단위로 묶어서 C# 코드로 메시(Mesh)를 하나하나 조립하는 중노동을 했습니다.

* **현대 유니티의 해결책**:\
유니티의 **`Tilemap`** 과 **`Tilemap Renderer`** 컴포넌트를 사용하세요. 기획자가 화면에 타일을 1만 개 깔아도, 유니티 엔진이 C++ 내부 단에서 알아서 1만 개의 타일을 뭉쳐 **'단 1개의 거대한 메쉬 덩어리'** 로 묶어버립니다 (배칭). \
화면에 보이는 수천 개의 타일이 **단 1번의 렌더링(Draw Call)** 으로 처리되는 최적화 컴포넌트입니다.

### 6.2 보이지 않는 것은 그리지 마라 (`Occlusion Culling`)
카메라 렌즈(절두체) 밖으로 나간 오브젝트는 유니티가 알아서 그리지 않습니다(`Frustum Culling`). \
하지만 카메라 안쪽이더라도, **거대한 성벽 뒤에 숨어서 안 보이는 몬스터 100마리**는 어떻게 될까요? \
기본적으로 유니티는 성벽 뒤의 몬스터도 다 계산하고 그립니다 (낭비).\
맵에 `Static` 체크를 하고 **`Occlusion Culling(오클루전 컬링)`** 을 구워주면(Bake), 벽 뒤에 가려져서 내 눈에 안 보이는 오브젝트들은 렌더러가 싹 다 꺼지며 프레임이 상승합니다.

## 7. 실습 문제 및 복습

**Q1. 게임 중에 몬스터 색상을 바꾸기 위해 `GetComponent<Renderer>().sharedMaterial.color = Color.red;` 코드를 실행했습니다. 어떤 부작용이 발생하나요?**
> `sharedMaterial`은 복사본을 만들지 않고 유니티 프로젝트 폴더에 있는 에셋 원본(`.mat` 파일)을 직접 건드립니다.\
> 따라서 씬에 존재하는 해당 머티리얼을 쓰는 모든 몬스터가 다 같이 빨간색으로 변해버리며, 심지어 게임(플레이 모드)을 종료해도 에디터 상에 빨간색으로 영구적으로 저장되어 원본 데이터가 오염되는 대참사가 벌어집니다.

**Q2. 파티클 이펙트나 투명한 유리창 등을 렌더링할 때 사용하는 `Material`의 `Surface Type`은 무엇이어야 하나요?**
> **Transparent (반투명)** 이어야 합니다. `Opaque(불투명)` 상태에서는 셰이더가 알파(Alpha, 투명도) 값을 무시하고 렌더링하므로 투명해지지 않고 검은색이나 단색으로 칠해져 버립니다.

**Q3. 캐릭터가 몬스터에게 은신 스킬을 써서 화면에서 보이지 않게 하려 합니다. `gameObject.SetActive(false)`를 쓰면 렌더링은 꺼지지만, 스킬 지속시간 카운트다운(Update) 코루틴까지 다 죽어버리는 문제가 생깁니다. 어떻게 해결해야 하나요?**
> 몬스터의 **`Renderer` 컴포넌트의 `enabled` 속성만 `false`로 꺼주면 됩니다.** 이렇게 하면 화면에 그리는 출력 과정(Draw)만 쏙 빠질 뿐, `GameObject` 자체는 살아 숨 쉬고 있으므로 `Update`의 카운트다운 로직이나 이동 로직은 완벽하게 정상 작동합니다.

## 8. 주의사항 및 안전 습관

* **`Line Renderer`의 배열 크기 할당**: `lineRenderer.SetPosition(0, pos)`를 부르기 전에 반드시 `positionCount = 2;` 처럼 몇 개의 점을 찍을지 배열 크기를 먼저 선언해 주어야 에러가 나지 않습니다.
* **`Trail Renderer`의 꼬리 청소(`Clear`)**: 오브젝트 풀링(Object Pooling)으로 썼던 총알을 거둬들여 다시 발사할 때, 궤적(Trail)을 `Clear()` 함수로 지워주지 않으면 예전 위치에서 지금 위치까지 화면을 가로지르는 흉측한 선이 그어지는 버그가 납니다.
* **`GetComponentsInChildren`의 오남용 금지**: 보스 몬스터 산하의 모든 자식 렌더러를 긁어오는 이 함수는 매우 무겁습니다. 절대 `Update`나 피격 순간마다 호출하지 말고, 무조건 `Awake`에서 딱 한 번 배열(Array)에 캐싱해두고 돌려 써야 합니다.
