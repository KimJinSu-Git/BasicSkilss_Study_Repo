# [Fundamentals] 1. Unity Engine 기초

## 1. Unity Engine 이란?
Unity Engine은 게임, 시뮬레이션, VR/AR 등 인터랙티브 3D 콘텐츠를 만드는 실시간 개발 플랫폼입니다. 단순히 "게임 엔진"이라기보다, 콘텐츠 제작에 필요한 거의 모든 기능(렌더링, 물리, 오디오, 애니메이션, UI, 네트워크)을 한곳에 통합한 종합 도구입니다.

> **종합 영화 스튜디오**
> * **Camera (카메라)** : 관객에게 장면을 어떻게 보여줄지 결정합니다.
> * **Lighting & Scene (조명과 세트장)** : 시각적 분위기와 무대를 구성합니다.
> * **GameObject (배우)** : 화면 속에 등장하는 모든 인물과 사물입니다.
> * **Component (배우의 소품/능력)** : 칼, 마법 스크롤, 갑옷 등 배우에게 쥐여주는 능력치입니다.
> * **C# Script (각본)** : 배우가 언제, 누구를 때리고, 어떻게 대사할지 지시합니다.
> * **Build (다양한 상영관)** : 만들어진 영화를 PC, 모바일, 콘솔, 웹 등 어디서든 틀 수 있게 변환합니다.

**왜 사용하는가?**\
게임 개발의 모든 단계(에셋 관리, 씬 구성, 코딩, 테스트, 빌드)를 하나의 에디터 안에서 처리할 수 있으며, 한 번 만든 게임을 iOS, Android, PC, 콘솔 등 20개가 넘는 플랫폼에 버튼 한 번으로 동시 배포(Cross-Platform)할 수 있기 때문입니다.

## 2. 핵심 요약

| 요소 | 한 줄 설명 |
| :--- | :--- |
| **통합 개발 환경** | 코드, 모델링 배치, 애니메이션, 테스트가 한 에디터 안에서 끝남 |
| **크로스 플랫폼** | 한 번의 C# 코드 작성으로 수많은 디바이스에 동시 배포 가능 |

| **C# 스크립팅** | `MonoBehaviour`를 상속받은 C# 클래스로 게임의 로직과 생명력을 불어넣음 |

## 3. 세부 개념 및 원리

### 3.1 Unity의 두 얼굴 — Editor & Runtime
* **Unity Editor (에디터)** : 개발자와 디자이너가 씬을 꾸미고, 코드를 연결하고, 수치를 조절하는 "콘텐츠 제작 환경"입니다.
* **Unity Runtime (런타임)** : 최종적으로 빌드된 게임이 플레이어의 스마트폰이나 PC에서 "실행되는 환경"입니다. 유니티는 에디터 내부에서도 [Play] 버튼을 눌러 이 런타임을 즉시 시뮬레이션할 수 있습니다.

### 3.2 컴포넌트 기반 아키텍처 (Component-Based)
유니티의 객체 지향은 상속(`is-a`)보다 **조합(`has-a`)** 을 압도적으로 선호합니다.\
`GameObject`라는 속이 텅 빈 레고 판때기에, 원하는 능력을 가진 레고 블록(`Component`)을 갖다 끼우는 방식입니다.

```text
GameObject (빈 그릇)
  ├─ Transform (위치, 회전, 크기) ➔ 우주에 존재하기 위한 필수 컴포넌트 (삭제 불가)
  ├─ MeshRenderer (시각 표시) ➔ 눈에 보이게 해줌
  ├─ BoxCollider (충돌 판정)  ➔ 벽을 뚫고 지나가지 않게 해줌
  ├─ Rigidbody (물리 엔진)    ➔ 중력을 받아 바닥으로 떨어지게 해줌
  └─ PlayerMove.cs (커스텀 스크립트) ➔ 키보드를 누르면 움직이게 해줌
```
**장점**: 상속의 한계인 "총을 들고 마법을 쓰는 좀비"를 만들 때, 복잡한 클래스 다중 상속을 짤 필요 없이 그냥 텅 빈 오브젝트에 `총 컴포넌트`, `마법 컴포넌트`, `좀비 컴포넌트`를 덕지덕지 붙이면 끝납니다.

## 4. 코드로 보는 Unity 스크립팅

### 4.1 가장 단순한 Unity 스크립트와 생명주기(Life Cycle)
C# 콘솔 앱은 `Main()` 함수부터 시작하지만, 유니티는 **엔진이 알아서 적절한 타이밍에 내 스크립트의 함수를 호출**해 줍니다.
```csharp
using UnityEngine; // 유니티 엔진의 모든 기능을 쓰기 위한 필수 네임스페이스

// 모든 유니티 스크립트는 MonoBehaviour를 상속받아야 컴포넌트로서 오브젝트에 붙일 수 있습니다.
public class HelloUnity : MonoBehaviour
{
    // Start: 이 컴포넌트가 태어날 때(게임이 시작될 때) 딱 1번만 불립니다. (초기화 역할)
    void Start()
    {
        Debug.Log("게임 시작. 체력을 100으로 채웁니다.");
    }

    // Update: 게임이 실행되는 동안 매 프레임(1초에 약 60번) 쉴 새 없이 불립니다. (실시간 로직)
    void Update()
    {
        // 매 프레임마다 Y축을 기준으로 회전시킵니다.
        transform.Rotate(0, 90f * Time.deltaTime, 0);
    }
}
```

### 4.2 Unity의 4대 핵심 클래스
| 클래스 | 역할 |
| :--- | :--- |
| **`GameObject`** | 씬에 존재하는 모든 엑스트라와 주연 배우들의 실체 (그릇) |
| **`Component`** | `GameObject`에 붙여서 능력을 부여하는 모든 부품들의 **최상위 부모 클래스** |
| **`Transform`** | `Component`의 자식이자, 위치/회전/크기를 담당하는 필수 장기 |
| **`MonoBehaviour`**| `Component`의 자식이자, 우리가 짜는 커스텀 C# 로직이 올라타는 기반 클래스 |

## 5. 프로젝트 시작 전 결정할 3가지

프로젝트를 세팅할 때 잘못 고르면 뼈저리게 후회하는 3대장입니다.

| 결정 항목 | 판단 기준 | 나중에 바꾸려 하면?                                                                         |
| :--- | :--- |:------------------------------------------------------------------------------------|
| **버전 (LTS vs Tech)** | 실무는 무조건 **LTS (Long Term Support)** 버전이 국룰. 1년 이상 안정화된 버전을 씁니다. | 엔진 업그레이드 시 수많은 에셋과 플러그인에서 빨간 에러 폭탄이 터짐.                                             |
| **렌더 파이프라인** | 모바일/캐주얼 ➔ **URP** (보편적) <br> 실사/AAA급 PC/콘솔 ➔ **HDRP** | **가장 비싼 결정.** 파이프라인을 바꾸면 기존 씬의 모든 빛(Light)과 머티리얼(재질)이 분홍색으로 깨지며 사실상 처음부터 다시 만들어야 함. |
| **2D vs 3D 템플릿** | 카메라 세팅, 중력축, 라이팅 기본값의 차이 | 비교적 저렴함. 나중에 에디터 설정(Project Settings)에서 수동으로 바꿔주면 됨.                                |

## 6. 실습 문제 및 복습

**Q1. "컴포넌트 기반 구조(Component-based Architecture)"는 무엇이고 객체 지향의 '상속'에 비해 왜 게임 개발에 유리한가요?**
> 하나의 빈 `GameObject`에 여러 부품(`Component`)을 레고 블록처럼 조합해 기능을 부여하는 방식입니다.\
> 상속은 부모-자식 관계가 굳어져서 다중 분류가 어렵지만, 컴포넌트 방식은 기능 단위로 쪼개져 있어 "날아다니며 불을 뿜는 독 개구리" 같은 기괴한 기획자의 요구사항도 기존 컴포넌트(`Fly`, `FireBreath`, `Poison`)들을 조합하기만 하면 즉각 대응할 수 있어 유연성과 재사용성이 압도적입니다.

**Q2. "Unity는 C#을 쓰니까 C++을 쓰는 언리얼보다 무조건 게임 성능이 떨어진다"는 주장을 반박해 보세요.**
> 반은 맞고 반은 틀립니다. C# 자체가 가비지 컬렉터(GC) 때문에 C++보다 상대적으로 무거운 것은 사실입니다. 하지만 유니티 엔진의 핵심 코어(물리, 렌더링)는 C++로 작성되어 있으며, 우리가 짠 C# 코드마저도 빌드 시점에는 **IL2CPP**라는 기술을 통해 C++ 코드로 변환되어 컴파일됩니다.\
> 최근에는 DOTS와 Burst Compiler 기술의 도입으로 네이티브 C++에 필적하는 성능을 내고 있어, 99%의 게임 개발에서 언어 차이로 인한 성능 이슈는 체감하기 어렵습니다.

**Q3. 유니티 씬(Scene)에 빈 오브젝트를 하나 만들었습니다. 이 오브젝트에서 절대 삭제할 수 없는 유일한 컴포넌트는 무엇이며 그 이유는 무엇인가요?**
> **`Transform`** 컴포넌트입니다. 유니티의 씬(3D 우주 공간)에 어떤 물체가 존재하려면 무조건 자기 자신의 좌표(위치), 회전값, 크기값을 가져야만 공간 상에 배치하고 렌더링할 수 있기 때문입니다.

## 8. 주의사항 및 안전 습관

* **모든 것을 `Update()`에 때려 넣지 마라**: 초보자들은 타이머, 입력 검사, 거리 계산 등 모든 로직을 1초에 60번 불리는 `Update`에 몰아넣어 엄청난 렉(프레임 드랍)을 유발합니다. 이벤트(Event)나 코루틴(Coroutine)을 활용해 호출 빈도를 최소화하세요.
* **버전 관리(Git) 주의사항**: 유니티 프로젝트를 Git으로 공유할 때 `Library/`, `Temp/`, `Build/` 폴더는 절대 커밋하면 안 됩니다. 오직 `Assets/`, `Packages/`, `ProjectSettings/` 폴더만 공유하며, 에디터 설정에서 버전 컨트롤 모드를 **`Visible Meta Files`** 로 두어야 에셋 참조가 끊기지 않습니다.
* **바퀴를 다시 발명하지 마라**: 직접 3주 동안 짤 시스템이 에셋 스토어(Asset Store)에 10달러에 팔고 있다면, 그냥 사서 쓰는 것이 좋습니다.
