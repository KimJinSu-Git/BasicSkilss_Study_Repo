# [Fundamentals] 8. Component (컴포넌트)

## 1. 컴포넌트(Component)란?
> **텅 빈 상자와 레고 부품**
> * **`GameObject`** 는 속이 텅 빈 상자입니다. 이 상자 자체는 화면에 보이지도, 굴러가지도 않습니다.
> * **`Component`** 는 그 상자에 끼워 넣는 **레고 부품**입니다. 어떤 부품을 꽂느냐에 따라 이 상자가 카메라가 되기도, 몬스터가 되기도 합니다.

**왜 이런 방식을 쓸까? (상속 vs 조합)**\
RPG 게임을 만들 때, "플레이어", "오크", "드래곤" 클래스를 일일이 상속(Inheritance)으로 나누다 보면 "독을 뿌리면서 날아다니는 은신 오크" 같은 혼종 기획이 나올 때 코드가 폭발합니다.\
유니티는 **조합(Composition)** 방식을 택했습니다. 그냥 텅 빈 오브젝트에 `[비행]`, `[독]`, `[은신]` 부품(컴포넌트)을 드래그해서 붙이면 끝납니다.
1. **재사용성**: `[체력]` 부품 하나를 짜서 플레이어, 보스, 심지어 부서지는 나무 상자에 그대로 꽂아 씁니다.
2. **유연성**: 게임 실행 중에 `[비행]` 부품을 떼어버리거나 꺼두면, 즉시 날개가 꺾인 추락 상태를 구현할 수 있습니다.

## 2. 핵심 요약

| 요소 | 한 줄 설명                                        |
| :--- |:----------------------------------------------|
| **`GameObject`** | 컴포넌트들을 담는 그릇 (컨테이너).                          |
| **`Transform`** | **절대 지울 수 없는 유일한 부품.** 모든 오브젝트는 우주 좌표를 가져야 함. |
| **`GetComponent<T>()`** | 내 몸통에 붙어있는 특정 부품(`T`) 하나를 찾아오는 무거운 함수.        |
| **`TryGetComponent<T>()`**| 부품이 없을 수도 있을 때, 에러 없이 안전하고 빠르게 찔러보는 함수.       |
| **`GetComponentsInChildren<T>()`**| 내 자식들(자손 포함)의 몸통을 다 뒤져서 부품을 싹 다 배열로 모아오는 함수.  |

## 3. 세부 개념 및 원리

### 3.1 주요 내장 컴포넌트 종류
유니티는 이미 수백 가지의 완성된 부품을 제공합니다. (우리가 짜는 스크립트도 결국 이 부품 중 하나입니다.)

| 컴포넌트 | 하는 일 (부여하는 능력) |
| :--- | :--- |
| **`Transform`** | 필수 장기. 위치, 회전, 크기를 관장합니다. |
| **`MeshRenderer`** / **`SpriteRenderer`** | 3D 모델이나 2D 그림을 화면에 **그려줍니다(시각화)**. |
| **`Collider`** | 벽을 뚫지 못하게 막는 껍데기 **(충돌체)**. |
| **`Rigidbody`** | 중력을 받고 부딪혀서 튕겨나가게 하는 **물리 엔진**. |
| **`AudioSource`** | 음악이나 효과음을 재생하는 **스피커**. |
| **`Animator`** | 걷기, 뛰기, 공격 등 동작을 제어하는 **애니메이션 컨트롤러**. |

### 3.2 어디까지 찾는가 — Get 계열 6가지 형제들
이름이 길지만 규칙은 2개뿐입니다. **`s`가 붙으면 배열(전부)**, **`In~`이 붙으면 계층(위아래)** 을 뒤집니다.

| 메서드 | 찾는 범위 | 반환값 (실패 시) |
| :--- | :--- | :--- |
| `GetComponent<T>()` | 내 몸통 | 첫 번째 부품 (`null`) |
| `GetComponents<T>()` | 내 몸통 | 부품 **배열** (빈 배열 `[]`) |
| `GetComponentInChildren<T>()` | **나 + 내 자식들** | 첫 번째 부품 (`null`) |
| `GetComponentsInChildren<T>()` | **나 + 내 자식들** | 부품 **배열** (빈 배열 `[]`) |
| `GetComponentInParent<T>()` | **나 + 내 부모(조상)**| 첫 번째 부품 (`null`) |
| `GetComponentsInParent<T>()` | **나 + 내 부모(조상)**| 부품 **배열** (빈 배열 `[]`) |

> **주의: `InChildren`은 '나(부모 자신)'부터 찾습니다!**\
> "자식들 것만 싹 다 줘!"라고 `GetComponentsInChildren`을 불렀는데 개수가 1개 더 많다면, **부모 몸통에 붙어있던 부품이 1번으로 딸려 들어온 것**입니다. 자식 것만 순수하게 원한다면 `if (item.gameObject == this.gameObject) continue;` 로 1번을 걸러내야 합니다.

## 4. 코드로 보는 컴포넌트 캐싱 (Caching)

`GetComponent`는 오브젝트의 가방을 싹 뒤지는 꽤 무거운 연산입니다. 매 프레임 부르면 게임에 렉이 걸립니다.

### 잘못된 코드 (매 프레임 뒤지기)
```csharp
void Update()
{
    if (Input.GetKeyDown(KeyCode.Space))
    {
        // 스페이스바 누를 때마다 내 몸을 뒤져서 부품을 찾음!
        // 만약 콜라이더를 실수로 지웠다면 이 줄에서 NullReferenceException 폭발
        GetComponent<BoxCollider>().enabled = false;
    }
}
```

### 정석 코드 (Awake 캐싱 + 안전 장치)
```csharp
// 안전벨트: "나를 오브젝트에 붙이려면 무조건 BoxCollider부터 달아놔라" (에디터 강제)
[RequireComponent(typeof(BoxCollider))]
public class JumpGood : MonoBehaviour
{
    private BoxCollider _boxCol; // 찾은 부품을 쥐고 있을 변수

    void Awake()
    {
        // 정석: 태어날 때 딱 한 번만 찾아서 내 변수(필드)에 저장(Cache)해둔다
        _boxCol = GetComponent<BoxCollider>();
    }

    void Update()
    {
        if (Input.GetKeyDown(KeyCode.Space))
        {
            // 찾을 필요 없이 쥐고 있는 변수를 바로 쓴다 (비용 0)
            _boxCol.enabled = false;
        }
    }
}
```

## 5. 실전 활용: `TryGetComponent`

내가 때린 상대가 '일반 벽'인지, 체력이 있는 '몬스터'인지 모를 때가 있습니다.

```csharp
private void OnTriggerEnter(Collider other)
{
    // 과거 방식: 무작정 찾고, null인지 검사함 (코드가 길고 메모리 낭비)
    // Enemy enemy = other.GetComponent<Enemy>();
    // if (enemy != null) { enemy.TakeDamage(10); }

    // 최근 방식 : "혹시 너 Enemy 부품 달고 있니?" (에러 없이 찔러보기)
    if (other.TryGetComponent(out Enemy enemy))
    {
        enemy.TakeDamage(10); // 부품이 있으면 데미지를 준다
    }
    else
    {
        Debug.Log("이 녀석은 체력이 없는 무생물이군.");
    }
}
```

> **[최적화 팁] `CompareTag`를 먼저 써라**\
> 총알이 초당 100발씩 날아다닐 때 매번 `TryGetComponent`를 찌르는 것도 부담될 수 있습니다.\
> 유니티에서 가장 싼(가벼운) 문자열 검사인 태그(Tag)를 먼저 확인하세요.\
> `if (other.CompareTag("Enemy")) { other.GetComponent<Enemy>().TakeDamage(10); }`

## 6. 지침서: 인스펙터 꽂기 vs 런타임 수집하기

카드 짝맞추기 게임에서 카드 20장을 매니저에게 인식시키는 2가지 방법의 장단점입니다.

| 축 | 1. 수동 배선 `[SerializeField] Card[]` | 2. 자동 수집 `GetComponentsInChildren()` |
| :--- | :--- | :--- |
| **순서 지정** | 내가 인스펙터에 꽂은 순서가 절대적 | 하이어라키(트리)의 위아래 순서대로 자동 정렬 |
| **개수 추가** | 카드를 1장 더 만들면 인스펙터 칸을 늘려 **또 드래그해줘야 함** | 하이어라키 자식으로 넣기만 하면 **자동으로 빨려 들어옴** |
| **비활성화 객체** | 꺼둔(Disable) 카드도 완벽하게 물고 있음 | 기본적으로 꺼둔 카드는 배열에서 **빠져버림** (옵션으로 켤 수 있음) |
| **디버깅(에러)**| 내가 연결을 빼먹은 **빈칸(None)이 눈에 확 보임** | 배열 개수가 0개여도 **눈에 안 보이고 조용히 고장남** |

* **결론**: 순서가 기획적으로 중요한(1번 자리, 2번 자리) 녀석들은 인스펙터 배선, 순서 상관없이 적이나 코인들을 뭉탱이로 껐다 켜야 할 때는 자동 수집이 유리합니다.

### 인스펙터 다차원 배열 우회하기
유니티 인스펙터는 2차원 배열 `public Card[,] board;`를 보여주지 못합니다. 1차원 배열로 풀어서 코드로 `i / 열`, `i % 열` 계산을 하는 게 정석입니다.\
하지만 기획자가 인스펙터에서 격자(Grid) 모양으로 카드를 세팅하고 싶어 한다면?

```csharp
[System.Serializable] // 구조체나 클래스에 이걸 붙이면 유니티 인스펙터에 노출됩니다
public class CardRow
{
    public Card[] columns; // 가로 한 줄의 카드들
}

public class BoardManager : MonoBehaviour
{
    // 세로 열을 추가하면, 인스펙터에서 2차원 배열처럼 관리할 수 있는 꼼수 완성
    [SerializeField] private CardRow[] boardRows; 
}
```

## 7. 실습 문제 및 복습

**Q1. 스크립트 코드 안에서 이 오브젝트에 부착된 `BoxCollider`를 지우고 싶습니다. `Destroy(this)`를 쓰면 될까요?**
> 안 됩니다. `this`는 이 스크립트 컴포넌트 자기 자신을 의미하므로, 이 스크립트가 파괴됩니다.\
> 올바른 방법은 `Destroy(GetComponent<BoxCollider>());` 처럼 지우고자 하는 해당 부품(콜라이더)을 콕 집어서 `Destroy` 함수에 넘겨주어야 합니다. (참고로 `Destroy(gameObject)`를 하면 상자 자체가 폭파됩니다.)

**Q2. 자식 오브젝트들에 흩어져 있는 `Renderer` 부품들을 모으기 위해 `GetComponentsInChildren<Renderer>()`를 썼습니다. 그런데 하이어라키에서 자식들의 순서를 마우스 드래그로 위아래로 섞었더니, 배열에 들어온 부품들의 순서도 바뀌어 버렸습니다. 왜 그런가요?**
> `GetComponentsInChildren`은 하이어라키 계층 창에 보이는 순서(위에서 아래로 깊이 우선 탐색)대로 부품을 긁어모아 배열을 만듭니다.\
> 따라서 하이어라키 순서를 바꾸면 수집 순서도 바뀌므로, 이 배열의 인덱스 순서에 의존하는 로직(예: 0번은 머리, 1번은 몸통)을 짜면 매우 위험합니다.

**Q3. 매 프레임 적의 체력을 닳게 하기 위해 `Update()` 안에 `GetComponent<Health>().hp -= 1;`을 썼습니다. 이 코드가 최악인 2가지 이유를 대보세요.**
> 1. `GetComponent`는 무거운 탐색 함수인데 이를 1초에 60번씩 부르면 심각한 성능 저하(렉)가 발생합니다. (`Awake`에서 1번만 캐싱해야 함)
> 2. 만약 해당 오브젝트에 `Health` 컴포넌트가 지워졌거나 없다면, `null`을 반환하게 되고, 거기에 `.hp`를 접근하려 했으므로 `NullReferenceException` 폭탄이 터져 Update 문 전체가 멈춰버립니다.

## 8. 주의사항 및 안전 습관

* **`RequireComponent`를 습관화하라**: 내가 짠 스크립트가 무조건 콜라이더를 필요로 한다면, 클래스 위에 `[RequireComponent(typeof(BoxCollider))]`를 달아주세요. 동료가 스크립트만 띡 붙였을 때 자동으로 콜라이더까지 생성해 주는 최고의 방어막입니다.
* **비활성화 컴포넌트 수집의 함정**: 자식들 중에 꺼둔(Disabled) 오브젝트가 있다면 `GetComponentsInChildren` 배열에 들어오지 않습니다. 꺼둔 놈까지 싹 다 필요하다면 `GetComponentsInChildren<T>(true)` 처럼 파라미터로 `true`를 줘야 합니다.
* **너무 거대한 컴포넌트를 만들지 마라**: `Player.cs` 하나에 이동, 점프, 피격, 사운드, 인벤토리 로직을 다 때려 넣으면 스파게티 코드가 됩니다. `PlayerMove`, `PlayerHealth`, `PlayerSound` 등으로 레고 블록을 잘게 쪼개는 것이 진정한 컴포넌트 패턴의 미덕입니다.
