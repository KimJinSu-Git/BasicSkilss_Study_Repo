# [Fundamentals] 18. ScriptableObject

## 1. ScriptableObject 란?
> **'부품'과 '설명서'**
> * **`MonoBehaviour` (부품)** : 게임 오브젝트에 착 달라붙어서 무언가 행동을 하는 부품입니다. 씬이 바뀌면 같이 죽습니다.
> * **`ScriptableObject` (설명서)** : "이 검의 공격력은 15이고, 불 속성이다"라는 정보를 담고 있는 독립적인 **데이터 설명서(파일)** 입니다. 하이어라키(씬)에 존재하지 않으며 프로젝트 폴더에 `.asset` 파일로 꽂혀 있습니다.

**왜 필요한가?**
1. **코드 하드코딩 방지**: `int attackPower = 15;`라고 코드에 냅다 적어두면, 밸런스를 고칠 때마다 코드를 열고 컴파일을 기다려야 합니다. 프로그래머가 아니면 손을 댈 수가 없습니다.
2. **프리팹의 메모리 낭비 방지**: 슬라임 100마리가 스폰될 때, 각 슬라임이 "슬라임 체력은 20"이라는 동일한 데이터를 100개씩 짊어지고 다닙니다. 이 공통된 수치를 프리팹 밖으로 빼서 1벌로 줄일 수 있습니다.
3. **에셋 참조의 편리함**: CSV나 엑셀 파일에는 유니티의 `Sprite`나 `GameObject` 프리팹을 집어넣을 수 없습니다. 반면 `ScriptableObject`는 유니티 친화적이라 인스펙터에 스프라이트나 브금을 바로 끌어다 놓을 수 있습니다.

## 2. 핵심 요약

| 비교 축 | `MonoBehaviour` | `ScriptableObject` |
| :--- | :--- | :--- |
| **태생(위치)** | 하이어라키 창의 오브젝트에 빌붙어 삼 | 프로젝트 창(`Assets` 폴더)의 단독 파일 |
| **메모리 복제** | 복제된 개수만큼 데이터도 N벌 복제됨 | **에셋 파일 하나를 N명이 참조(공유)함** |
| **생존 주기** | 씬 파괴 시 함께 죽음 | 씬과 무관하게 영생함 |
| **Update** | 있음 | 없음 |
| **생성 방법** | `Add Component`로 오브젝트에 부착 | 우클릭 ➔ `Create` 메뉴로 에셋 파일 생성 |

> **[원칙]**
> 1. **"종류는 에셋이 들고, 상태는 컴포넌트가 든다."** (체력 최대치 100은 에셋에, 깎여나가는 현재 체력은 MonoBehaviour에 둡니다.)
> 2. `ScriptableObject`의 데이터는 코드로 절대 수정하지 마세요. (읽기 전용 프로퍼티 필수) 런타임에 수정하면 유니티 에디터 원본 파일 자체가 오염됩니다.
> 3. 클래스명과 스크립트 파일명(`.cs`)이 대소문자까지 똑같아야 엔진이 인식합니다

## 3. 세부 개념 및 원리

### 3.1 만드는 순서 — 두 줄과 클릭 한 번
준비물은 단 2개입니다. `ScriptableObject` 상속과 그 위에 달아주는 `[CreateAssetMenu]` 태그

~~~csharp
using UnityEngine;

// 프로젝트 창 우클릭 Create 메뉴에 나만의 에셋 생성 버튼을 만들어 줍니다.
[CreateAssetMenu(fileName = "NewItemData", menuName = "Game Data/Item", order = 1)]
public class ItemData : ScriptableObject
{
    // 절대 public으로 두지 마세요. 누군가 런타임에 값을 건드리면 원본 파일이 영구 오염됩니다.
    [SerializeField] private int id;
    [SerializeField] private string itemName;
    [SerializeField] private Sprite icon; // 엑셀로는 불가능한 '에셋 직접 참조'의 강력함
    [SerializeField] private int price;

    // 외부에서는 읽기만 가능하도록 프로퍼티로 구멍을 뚫어줍니다.
    public int ID => id;
    public string ItemName => itemName;
    public Sprite Icon => icon;
    public int Price => price;
}
~~~

### 3.2 런타임 오염 방지와 상태의 분리
세일 이벤트로 물건 가격을 깎아야 할 때, 냅다 `itemData.price = 10;`을 해버리면 플레이를 멈춰도 원본 에셋의 가격이 10골드로 영원히 깎여버립니다. (MonoBehaviour와 정반대입니다.)\
그래서 **가변 데이터(상태)는 씬에 있는 부품(`MonoBehaviour`)이 들어야 합니다.**

~~~csharp
public class ShopSlot : MonoBehaviour
{
    // 변하지 않는 '종류' (원본 틀, 에셋 참조)
    [SerializeField] private ItemData data; 

    // 변하는 '상태' (이 슬롯만의 값, 할인율 등)
    private int discountRate = 20; 

    // 원본 에셋은 건드리지 않고 계산해서 낸다
    public int TodayPrice => data.Price * (100 - discountRate) / 100;
}
~~~

### 3.3 에셋은 참조로 나눠 씁니다 (Flyweight 패턴)
에셋 하나를 여러 오브젝트가 가리켜(참조) 메모리를 절약합니다. 반대로 이 개체만의 완전한 독립적 복사본이 필요하다면 `Instantiate`로 에셋 자체를 복제할 수 있습니다.
~~~csharp
ItemData shared = database.FindOrNull(itemId); // 단순 참조 (모두가 같은 걸 봄)
ItemData copy = Instantiate(shared);           // 완전 복제 (원본에 영향 안 줌)
ItemData runtimeOnly = ScriptableObject.CreateInstance<ItemData>(); // 파일 없는 허공의 인스턴스
~~~
실무에서는 대개 복제하지 않습니다. 내구도처럼 달라지는 상태는 개별 클래스(`MonoBehaviour`)가 들고 있는 것이 훨씬 깔끔하기 때문입니다.

### 3.4 `ScriptableObject`의 생명주기
씬에 존재하는 오브젝트가 아니기 때문에 `Update`나 `Start`, 코루틴이 아예 없습니다.\
대신 에디터에서 기획자의 실수를 막아주는 정말 강력한 함수를 제공합니다.

~~~csharp
public class ItemData : ScriptableObject
{
    // 에디터에서 기획자가 인스펙터 값을 고친 바로 그 찰나의 순간에 유니티가 호출해 줍니다
    private void OnValidate()
    {
        if (price < 0)
        {
            Debug.LogError($"[{name}] 가격은 음수일 수 없습니다. 강제로 0으로 되돌립니다.");
            price = 0; // 실수로 엑셀에 마이너스 입력한 걸 유니티가 바로 차단해버림
        }
    }
}
~~~
*(참고: `OnEnable`은 에디터와 빌드 환경에서 호출 시점이 다르므로, 여기서 딕셔너리(색인)를 미리 만들어두는 것은 매우 위험합니다.)*

## 4. 실전 활용 예시 1: 데이터베이스 색인(Dictionary)화

아이템 에셋이 100개 있을 때, 코드로 "1001번 아이템 주세요"라고 매번 `for`문 배열을 훑으면 성능이 박살 납니다.\
데이터베이스 자체도 `ScriptableObject`로 만들고, 처음 찾을 때 **딕셔너리(Dictionary)** 로 색인(Index)을 파두는 최적화 팁입니다.

~~~csharp
using System.Collections.Generic;
using UnityEngine;

[CreateAssetMenu(fileName = "ItemDatabase", menuName = "Game Data/Item Database")]
public class ItemDatabase : ScriptableObject
{
    // 기획자가 인스펙터에서 100개의 아이템 에셋을 끌어다 놓을 배열
    [SerializeField] private ItemData[] items; 

    // O(1)의 속도로 빛처럼 찾게 해줄 캐싱 딕셔너리
    private Dictionary<int, ItemData> indexById; 

    // 딕셔너리를 필요할 때만 캐싱(예열)하는 함수
    private void EnsureIndex()
    {
        if (indexById != null) return; 

        indexById = new Dictionary<int, ItemData>();

        for (int i = 0; i < items.Length; ++i)
        {
            ItemData item = items[i];
            if (item == null) continue;
            
            // 멍청한 휴먼 에러(ID 중복) 방어 코드
            if (indexById.ContainsKey(item.ID)) 
            {
                Debug.LogWarning($"[{name}] 번호가 겹칩니다: {item.ID}");
                continue;
            }
            indexById.Add(item.ID, item);
        }
    }

    // 외부에서 아이템을 요청할 때 부르는 함수 (못 찾으면 null 반환)
    public ItemData FindOrNull(int id)
    {
        EnsureIndex(); // 딕셔너리 세팅 보장
        
        if (indexById.TryGetValue(id, out ItemData found)) return found;

        Debug.LogError($"[{name}] 없는 번호로 찾았습니다: {id}");
        return null; 
    }
}
~~~
이 구조를 통해 저장 파일(세이브)에는 아이템의 무거운 정보 대신 딱 `번호(ID)` 하나만 가볍게 적어두게 됩니다.

## 5. 실전 활용 예시 2: 엑셀(CSV)과 ScriptableObject의 결합

실무 기획자들은 수십 마리의 몬스터 밸런스를 일일이 유니티 에셋 창을 열고 수정하지 않고 엑셀(CSV)로 작업합니다.\
이때 **"수치는 텍스트 표(CSV)가 들고, 그림(에셋)은 ScriptableObject가 드는 혼종 기법"** 이 가장 많이 쓰입니다.

~~~csharp
[CreateAssetMenu(fileName = "SpriteTable", menuName = "Game Data/Sprite Table")]
public class SpriteTable : ScriptableObject
{
    // 코드로 CSV를 읽었더니 "슬라임 이미지 Key: 50"이라고 적혀있었다.
    // 그 50번을 이 테이블에 던져주면 실제 유니티 Sprite 파일로 교환해주는 전당포 같은 역할을 함.
    
    [SerializeField] private SpriteEntry[] entries;
    [SerializeField] private Sprite fallbackSprite; // 에러 났을 때 보여줄 물음표 대체 그림

    private Dictionary<int, Sprite> spriteByKey;

    // 대체 그림 연결 빠뜨림 방지
    private void OnValidate()
    {
        if (fallbackSprite == null)
            Debug.LogError($"[{name}] 못 찾았을 때 돌려줄 그림(Fallback)이 없습니다.");
    }

    public Sprite GetSprite(int key)
    {
        EnsureIndex(); // (딕셔너리 만드는 로직 생략)

        if (spriteByKey.TryGetValue(key, out Sprite found)) return found;

        Debug.LogError($"[{name}] 없는 Key로 그림을 찾았습니다: {key}");
        return fallbackSprite; // null을 던지면 UI가 먹통이 되므로 무조건 대체 깍두기 이미지를 던짐
    }
}
~~~

## 6. Unity 최적화 팁

### 6.1 규모의 벽: 언제 `ScriptableObject`를 떠나야 할까?
* **소규모 (종류가 50개 이하)**: 그냥 종류별로 `.asset` 파일을 만드는 게 유니티 에디터와 찰떡궁합이라 가장 편합니다.
* **대규모 (종류가 100개 이상)**: 몬스터 200마리를 폴더에 파일 200개로 쪼개 놓으면 밸런스를 한눈에 훑어볼 수가 없습니다. 이때는 무조건 **엑셀(CSV/JSON)** 표기법으로 탈출해야 합니다.
* **라이브 서버 패치**: 앱스토어 업데이트 없이 서버에서 몬스터 공격력을 올리고 싶다면, 빌드에 박혀버리는 `ScriptableObject`로는 불가능합니다. 서버에서 JSON 데이터를 받아오도록 설계해야 합니다.

### 6.2 프리팹을 '종류(Type)'로 쓸 때의 함정
몬스터 종류를 나누기 귀찮아서 그냥 `Slime`, `Orc` 프리팹 자체를 종류 구분용으로 쓰면 벌어지는 참사입니다.
~~~csharp
// 함정: 참조 비교
// 밭에 방금 심겨진 당근(사본)과 인스펙터에 꽂아둔 당근 프리팹 원본(틀)은 태생부터 다른 물건입니다
if (plantedCrop == carrotPrefab) { } // ➔ 무조건 false가 뜹니다

// 정석: 번호(ID) 비교 (종류를 가리키는 값으로 본다)
if (plantedCrop.ID == carrotPrefab.ID) { }
~~~
이러한 혼동을 막기 위해, 데이터는 `ScriptableObject`가 들고 개체는 그걸 가리키는 포인터 역할만 하게끔 철저히 분리해야 합니다.

## 7. 실습 문제 및 복습

**Q1. `WeaponData` ScriptableObject를 만들고 필드 변수인 `public int attack;`을 씬에 있는 코드로 수정(`data.attack = 100;`)했습니다. 게임을 정지(Stop)하고 인스펙터를 확인해보니 공격력이 원래대로 돌아오지 않고 100으로 저장되어 버렸습니다. 이유가 무엇이며 어떻게 설계해야 하나요?**
> `ScriptableObject`는 씬에 종속된 일회성 오브젝트가 아니라 프로젝트 폴더에 존재하는 실제 '에셋 파일'입니다.\
> 에디터 런타임에 값을 바꾸면 원본 파일 자체가 오염(수정)되어 버립니다.\
> 따라서 원본 에셋의 필드는 무조건 `[SerializeField] private`으로 감추고, 코드가 원본 데이터를 덮어쓰지 못하도록 읽기 전용 속성(Property)만 열어두는 것이 필수 안전 규칙입니다.

**Q2. `ItemDatabase` ScriptableObject 안의 `OnEnable()` 이벤트 함수 안에 딕셔너리(캐싱)를 만드는 코드를 넣었습니다. 이 코드가 실무에서 끔찍한 버그를 유발할 수 있는 '환경적 차이'는 무엇인가요?**
> `OnEnable`이 호출되는 타이밍이 에디터와 빌드 환경에서 완전히 다릅니다.\
> 에디터에서는 스크립트 코드를 수정하고 컴파일할 때마다 `OnEnable`이 제멋대로 불리지만, 모바일로 빌드된 폰에서는 에셋이 처음 메모리에 로드될 때 한 번 불립니다.\
> 이렇게 호출 시점이 불안정하므로 캐싱 작업은 `OnEnable`이 아니라, 누군가 최초로 데이터를 요청(`FindOrNull`)하는 순간(Lazy Initialization)에 수행하는 것이 가장 안전합니다.

**Q3. `ScriptableObject` 에셋 안에 `Update()` 함수를 작성하면 어떻게 되나요?**
> 컴파일 에러는 나지 않지만, 게임을 켜도 영원히 단 한 번도 실행되지 않습니다.\
> `ScriptableObject`는 씬 하이어라키에 올라가는 생명체(`GameObject`)가 아니기 때문에, 부를 자리가 없어 유니티 엔진의 메인 루프(매 프레임 호출) 사이클에 편입되지 못합니다.

## 8. 주의사항 및 안전 습관

* **스크립트명 = 클래스명 100% 일치**: "클래스는 `PotionData`인데 스크립트 파일명은 `ItemData.cs`로 되어 있네?" ➔ 바로 유니티가 클래스를 찾지 못해 Create 메뉴가 증발합니다. 무조건 일치시키세요.
* **`Resources` 폴더 남용 금지**: "코드로 `Resources.Load("ItemData")` 해야지!" ➔ `Resources` 폴더 안에 있는 모든 파일은 사용 여부와 상관없이 게임 시작 시 메모리 덩어리로 통째로 빌드됩니다. 첫 로딩을 느리게 만드는 주범이므로 가급적 인스펙터에서 직접 `[SerializeField]`로 꽂아 쓰세요.
* **조회 함수의 반환값은 폴백(Fallback) 처리하라**: 못 찾았다고 무책임하게 `null`을 뱉으면 부르는 쪽에서 연쇄 폭발(`NullReferenceException`)이 일어납니다. 못 찾았으면 차라리 에러 로그를 남기고 물음표 모양의 대체 그림(`Fallback Sprite`)을 던져주어야, 에러로 게임이 터지는 걸 막고 기획자가 빠르게 오타를 눈치챌 수 있습니다.
* **배열을 보기 좋게 (ToString 팁)**: 배열 인스펙터가 `Element 0`, `Element 1`로 떠서 답답하다면, 해당 데이터 클래스 위에 `[Serializable]`을 얹고 안에 `public string name;` 변수 등을 활용해 보세요. 인스펙터 관리가 훨씬 깔끔해집니다.
