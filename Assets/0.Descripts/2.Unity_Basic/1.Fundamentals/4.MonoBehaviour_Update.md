# [Fundamentals] 4. 첫 스크립트 (MonoBehaviour · Update)

## 1. 스크립트와 MonoBehaviour 란?
C# 콘솔 프로그램은 내가 쓴 `Main()` 함수부터 시작해 내가 짠 순서대로 주도적으로 흐릅니다. 하지만 유니티는 정반대입니다.

> **무대 감독과 대기 중인 배우**
> * 프로그램의 전체 흐름(무대)은 유니티 엔진(무대 감독)이 꽉 쥐고 있습니다.
> * 내 스크립트는 무대를 돌리는 주체가 아니라, **"감독님, 제 차례(시점)가 오면 저를 불러 주세요"** 라고 등록해 두고 대기하는 **배우**입니다.
> * 엔진이 큐(Cue) 사인을 주면, 스크립트는 무대에 나가 배정된 대사(`Awake`, `Start`, `Update`)를 읊고 재빨리 빠집니다.

**왜 이런 구조가 필요한가?**\
게임 화면은 1초에 60번씩 다시 그려집니다. 그 짧은 찰나에 유저 입력을 읽고, 100마리 몬스터의 위치를 옮기고, 충돌을 검사해야 합니다.\
이 거대한 무한 반복문(Game Loop)을 내가 직접 짜려면 코드가 터져버립니다. 유니티는 이미 그 완벽한 뼈대(엔진)를 갖고 있습니다. 우리가 짤 코드는 그 뼈대 사이에 쏙쏙 끼워 넣을 **부품 조각**일 뿐이며, 그 부품을 끼울 수 있게 잭(Jack)을 만들어 주는 것이 바로 **`MonoBehaviour`** 클래스입니다.

## 2. 핵심 요약

| 키워드 | 하는 일 | 기억할 한 줄                               |
| :--- | :--- |:--------------------------------------|
| **`MonoBehaviour`** | 내 스크립트가 유니티 컴포넌트로서 동작하게 해주는 부모 클래스 | **이 상속을 지우면 오브젝트에 스크립트를 붙일 수 없습니다.**  |
| **`Awake()`** | 오브젝트가 씬에 태어날 때 **딱 한 번** 불림 | **"내 것"** 을 초기화하는 자리 (스크립트가 꺼져있어도 불림) |
| **`Start()`** | 첫 `Update()`가 시작되기 직전에 **딱 한 번** 불림 | **"남의 것"** 을 참조하는 자리 (스크립트가 켜져야만 불림)  |
| **`Update()`** | 게임이 도는 동안 **매 프레임마다 계속** 불림 | 사용자 입력, 이동 등 실시간 로직 처리                |
| **`Time.deltaTime`**| 이전 프레임에서 현재 프레임까지 걸린 시간 (초) | **이걸 곱해야 컴퓨터 사양에 상관없이 속도가 똑같아짐**      |

## 3. 세부 개념 및 원리

### 3.1 스크립트의 생성과 부착 (함정 주의)
1. **생성**: Project 창에서 우클릭 ➔ `Create` ➔ `C# Script` (또는 `MonoBehaviour Script`)
2. **이름 짓기**: 만들어진 직후 즉시 이름을 정합니다. **이때 지은 이름이 클래스 이름이 됩니다.**
3. **부착**: 스크립트를 Hierarchy의 게임 오브젝트로 드래그 앤 드롭합니다.

> **[입문자 단골 에러] 파일 이름과 클래스 이름의 불일치**\
> 대충 만들고 나중에 파일 이름을 `PlayerMove.cs`로 바꿨는데, 파일 안의 코드는 여전히 `class NewBehaviourScript`로 남아있다면?\
> ➔ 유니티는 **파일 이름과 클래스 이름이 다르면 오브젝트에 절대 붙여주지 않습니다**\
> ➔ 에러 메시지: *Can't add script component... because the script class cannot be found*

### 3.2 내가 부르지 않는데 어떻게 실행될까? (엔진의 마법)
```csharp
using UnityEngine; // 유니티 핵심 기능(MonoBehaviour, Debug 등)이 들어있는 주머니

public class FirstScript : MonoBehaviour // 이 상속이 있어야 유니티가 배우로 인정해 줌
{
    // 접근 제한자가 private이어도 유니티 엔진이 알아서 무시하고 찔러서 호출해 줍니다
    private void Start() 
    {
        Debug.Log("[FirstScript] 게임 시작!");
    }
}
```
유니티는 엔진 내부에서 **"이름(문자열)"**으로 함수를 찾아냅니다.\
그래서 `Start`를 `private`으로 둬도 유니티 엔진이 억지로 찾아내서 실행해 줍니다.\
하지만 이 방식에는 단점이 있습니다.

> **함수 이름을 틀려도 오류가 나지 않는다!**\
> 실수로 `void Updata()` 라고 스펠링을 틀리게 적어도, 유니티는 그저 "아, 얜 업데이트 안 쓰는 애구나" 하고 넘겨버립니다. 에러도 안 나고 경고도 안 나는데 캐릭터가 안 움직인다면 스펠링부터 확인하세요

### 3.3 프레임 독립성(Frame Independence)과 `Time.deltaTime`
`Update()`는 화면이 한 번 깜빡일 때(1 프레임) 한 번씩 실행됩니다.
* 좋은 컴퓨터 (60 FPS) ➔ 1초에 60번 실행됨
* 똥컴 (30 FPS) ➔ 1초에 30번 실행됨

```csharp
// 똥컴과 좋은 컴의 게임 속도가 달라지는 재앙의 코드
transform.position += Vector3.right * 1f; 
```
위 코드대로면 좋은 컴은 1초에 60칸을 이동하고, 똥컴은 30칸만 이동합니다.
이를 맞추기 위해 **`Time.deltaTime`(한 프레임당 걸린 시간, 예: 0.016초)** 을 곱해줍니다.

* 공식: **이번 프레임 이동 거리 = 1초당 원하는 속도 × `Time.deltaTime`**
* 활용: 타이머 만들기 ➔ `흐른 시간 += Time.deltaTime;`

### 3.4 Awake vs Start (분리 기준)
* **`Awake()`**: 모든 오브젝트가 막 태어난 시점. **자기 자신(내 것)의 변수를 세팅**하거나, 내 오브젝트에 붙은 컴포넌트를 가져올 때 씁니다. (인스펙터 체크박스를 꺼놔도 무조건 실행됨)
* **`Start()`**: 모든 오브젝트의 `Awake`가 싹 다 끝난 후 실행됨. **남의 것(다른 오브젝트)의 정보를 안전하게 가져와야 할 때** 씁니다. (체크박스가 켜져 있어야 실행됨)

## 4. 코드로 보는 `Time.deltaTime`의 위력

같은 요구사항("오브젝트를 위로 초당 2유닛씩 올린다")을 두 방식으로 비교합니다.

### 사양 타는 게임 (Before)
```csharp
using UnityEngine;

public class NaiveRiser : MonoBehaviour
{
    private void Update()
    {
        // 1프레임당 무조건 0.05 이동. 
        // 144Hz 모니터 쓰는 사람은 하늘로 승천해 버림.
        transform.position += Vector3.up * 0.05f; 
    }
}
```

### 완벽하게 동기화된 게임 (After)
```csharp
using UnityEngine;

public class PerfectRiser : MonoBehaviour
{
    // [SerializeField]: 코드는 private으로 보호하되, 인스펙터 창에서만 기획자가 편하게 수정 가능
    [SerializeField] private float riseSpeed = 2f; 

    private void Update()
    {
        // Vector3.up (위쪽) * 초당 2유닛 * 델타타임 보정
        // 누가 어떤 컴퓨터로 하든 정확히 1초에 2유닛씩 올라감
        transform.position += Vector3.up * riseSpeed * Time.deltaTime;
    }
}
```

## 5. 실전 활용 예시 (5초 뒤 떠오르는 발판)

코루틴이나 애니메이터 없이, 오직 `Update`와 `deltaTime`만으로 타이머를 구현하는 실무 기본기입니다.

```csharp
using UnityEngine;

public class DelayedRiser : MonoBehaviour
{
    [SerializeField] private GameObject targetObj;   // 인스펙터에서 띄울 오브젝트 연결
    [SerializeField] private float riseSpeed = 2f;   // 초당 상승 속도
    [SerializeField] private float waitSeconds = 5f; // 대기 시간 (5초)

    private float _elapsedTime; // 흐른 시간 (런타임에만 변하는 값이니 인스펙터 노출 X)
    private bool _isRising;     // 상승 시작 여부

    private void Update()
    {
        // 1. 아직 상승할 때가 아니라면 시간만 잰다
        if (!_isRising)
        {
            _elapsedTime += Time.deltaTime; // 스탑워치
            if (_elapsedTime >= waitSeconds) 
            {
                _isRising = true; // 5초 달성. 상태 전환
            }
            return; // 이번 프레임은 여기서 조용히 끝
        }

        // 2. 5초가 지났다면 매 프레임 위로 밀어 올린다
        targetObj.transform.position += Vector3.up * riseSpeed * Time.deltaTime;
    }
}
```
**이 코드의 가치**:\
변수 `_elapsedTime`은 `Update()` 함수가 끝나도 메모리에서 사라지지 않는 클래스 필드(멤버 변수)입니다. 이 변수에 `deltaTime`을 매 프레임 조금씩 누적해 더하는 것만으로 **"5초 뒤에 발동"** 이라는 시간이 완성됩니다.

## 6. 실습 문제 및 복습

**Q1. 스크립트 파일을 만들고 이름을 나중에 `PlayerController`로 수정했는데, 유니티 큐브에 드래그해도 스크립트가 붙질 않습니다. 에러 창도 안 뜨는데 원인이 무엇일까요?**
> 스크립트를 생성한 직후 이름을 바로 짓지 않고 엔터를 친 뒤 나중에 파일명만 수정하면, 윈도우 탐색기 상의 파일 이름(`PlayerController.cs`)과 코드 내부의 클래스 이름(`class NewBehaviourScript`)이 다르게 됩니다. **유니티는 이 둘의 이름이 정확히 일치하지 않으면 오브젝트에 컴포넌트로 붙여주지 않습니다.** 코드 에디터를 열어 클래스 이름을 파일명과 똑같이 맞춰주어야 합니다.

**Q2. `Update()` 함수 안에 적힌 코드가 1초에 실행되는 횟수는 고정되어 있나요? 아니라면 무엇에 의해 결정되나요?**
> 고정되어 있지 않습니다. `Update()`는 컴퓨터가 화면을 한 번 그릴 때(1 프레임) 한 번씩 호출됩니다. 따라서 유저의 **컴퓨터 사양(CPU/GPU 성능)과 씬의 복잡도**에 따라 초당 30번 불리기도, 144번 불리기도 합니다.

**Q3. 캐릭터의 이동 속도를 `public float speed = 5f;` 로 적지 않고 `[SerializeField] private float speed = 5f;` 로 적는 이유는 무엇인가요?**
> 둘 다 유니티 에디터 인스펙터 창에는 예쁘게 노출되어 기획자가 수치를 테스트할 수 있습니다.
> 하지만 `public`으로 열어버리면 다른 스크립트에서 이 캐릭터의 속도를 맘대로 건드릴 수 있어 치명적인 버그(캡슐화 파괴)를 유발합니다. `[SerializeField] private`는 **"에디터 편집의 편리함은 취하되, 코드 레벨에서의 방어력(`private`)은 굳건히 지키겠다"** 는 유니티 프로그래밍의 최고 모범 답안입니다.

## 7. 주의사항 및 안전 습관

* **함수명 스펠링을 목숨 걸고 확인하라**: `Awake`, `Start`, `Update`는 스펠링 대소문자 하나라도 틀리면 유니티가 조용히 호출을 무시합니다. 아무 에러도 안 나는데 코드가 안 돈다면 1순위로 함수명을 의심하세요.
* **이벤트 함수는 가급적 `private`으로 둬라**: `public void Update()`로 열어두면, 딴 놈이 내 업데이트를 억지로 두 번 부르는 대참사가 일어날 수 있습니다. 유니티 엔진은 `private`이어도 기가 막히게 찾아서 호출해 줍니다.
* **`Update` 안의 로그는 폭탄이다**: `Debug.Log` 하나 남기는 데 꽤 많은 메모리가 소모됩니다. 1초에 60번씩 콘솔창을 채우는 로그는 렉의 주범이니, 확인이 끝나면 반드시 주석 처리하거나 지우세요.
* **인스펙터 슬롯을 비워두지 마라 (`None`의 공포)**: 스크립트에 구멍을 파두고 씬에서 오브젝트 드래그 앤 드롭을 깜빡하면, 게임 실행 중 해당 코드를 부르는 순간 자비 없는 `NullReferenceException` 에러가 나며 기능이 죽어버립니다.
