# [메모리와 구조] 4. 힙 메모리 (Heap Memory)

## 1. 힙 메모리란?
스택(Stack)이 체계적으로 접시를 쌓아두는 단기 작업대였다면, 힙(Heap)은 거대하고 자유로운 **장기 보관 창고**입니다. 프로그램이 실행되는 동안 크기가 동적으로 변하거나, 메서드 호출이 끝나도 오랫동안 유지되어야 할 데이터들을 저장하는 거대한 메모리 공간입니다.

> **창고와 보관증 발급 카운터**
> * **`new`로 객체 생성** : 창고(힙)에 거대한 물건을 넣고, 그 위치가 적힌 작은 **보관증**을 발급받습니다.
> * **보관증 (스택의 참조 변수)** : 물건이 있는 창고의 위치(힙 주소)를 기록한 종이입니다.
> * **창고 관리인 (가비지 컬렉터, GC)** : 더 이상 어느 누구도 보관증을 가지고 있지 않은 물건(고아 객체)을 찾아내어 쓰레기통에 버리고 창고를 정리합니다.

**왜 필요한가?**
스택은 메서드가 종료되면 즉시 날아갑니다. 만약 무기를 하나 생성해서 플레이어가 죽을 때까지 들고 다녀야 한다면 스택만으로는 불가능합니다. 힙은 메서드의 생명주기와 무관하게 살아남는 객체들의 보금자리입니다.

## 2. 핵심 요약

| 특징 | 한 줄 설명                                           |
| :--- |:-------------------------------------------------|
| **역할** | 참조 타입(`class`, `array`, `string` 등) 데이터의 장기 저장소  |
| **할당** | **`new`** 키워드로만 동적 할당 가능                         |
| **해제** | **가비지 컬렉터(GC)** 가 자동 처리 ➔ 더 이상 아무도 참조하지 않는 객체 수거 |
| **크기 및 속도**| 스택보다 용량이 훨씬 크지만, 할당과 접근 속도는 스택보다 느림              |
| **생존 기간** | 프로그램 어딘가에서(변수, 컬렉션 등) 해당 주소를 **참조하는 한 계속 생존**    |
| **관리 주체** | .NET 런타임의 가비지 컬렉터 (개발자가 수동으로 삭제할 수 없음)           |

## 3. 세부 개념 및 원리

### 3.1 힙 할당: `new`의 마법
힙에 메모리를 할당하는 유일한 방법은 `new` 키워드입니다. `new ClassName()`이 실행되면 다음 일이 일어납니다.
1. 힙에서 객체 크기만큼의 빈 공간을 찾습니다. (이 과정이 스택보다 느림)
2. 공간을 할당하고 **생성자**를 호출하여 초기화합니다.
3. 그 힙 공간의 **시작 주소**를 반환하여 스택의 참조 변수(`obj`)에 저장합니다.

### 3.2 객체가 쓰레기(Garbage)가 되는 시점
GC는 힙을 쓱 훑어보며 "누구 나 쳐다보고 있는 사람(참조) 있어?"라고 묻습니다. 아무도 없으면 메모리에서 지웁니다.

| 시나리오 | 설명 |
| :--- | :--- |
| **스코프 종료** | 메서드가 끝나면서 스택에 있던 지역 참조 변수(보관증)가 날아간 경우 |
| **다른 객체 덮어쓰기** | `obj = new Player();` 로 새 주소를 덮어씌워 이전 객체가 고아가 된 경우 |
| **`null` 명시적 할당**| `obj = null;` 로 스스로 연결을 끊어버린 경우 |
| **컬렉션에서 제거** | `list.Remove(obj);` 로 리스트 안에서 주소를 지운 경우 |

### 3.3 메모리 누수(Memory Leak)의 함정
GC가 알아서 치워주는데 왜 메모리 누수가 발생할까요?\
**"우리는 지웠다고 생각했는데, 어딘가에 보관증(참조)이 남아있는 경우"** 입니다.
1. **정적(`static`) 컬렉션**: 객체를 담아놓고 `Remove`를 안 하면 게임이 꺼질 때까지 영원히 쌓입니다.
2. **이벤트(`Event`) 구독**: `A`가 `B.OnDeath += A.TakeAction`으로 구독하면, `B`가 `A`의 주소를 꽉 잡고 있습니다. `A`가 죽을 때 반드시 `-=` 로 구독 취소를 해야만 GC가 `A`를 수거해갑니다.

## 4. 코드로 보는 힙 메모리의 흐름

### 4.1 기본 할당과 객체 분리
```csharp
public class Player { public string Name; }

// 1. 힙에 1번 객체 할당, 스택의 p1이 주소를 가짐
Player p1 = new Player(); 
p1.Name = "전사";

// 2. 힙에 2번 객체 할당, 스택의 p2가 주소를 가짐
Player p2 = new Player(); 
p2.Name = "마법사";

// 3. 배열 생성: 힙에 주소를 담을 '슬롯 5개'짜리 배열 객체 할당
Player[] party = new Player[5];
// 각 슬롯마다 실제 힙 객체를 가리키도록 또 new를 해줘야 함
party[0] = new Player(); 
```

### 4.2 흔한 실수와 방어 코드 (컬렉션 참조)
```csharp
public class GameManager
{
    // static이므로 이 리스트는 게임 내내 절대 죽지 않습니다.
    public static List<Monster> AllMonsters = new List<Monster>();

    public void SpawnMonster()
    {
        Monster m = new Monster();
        AllMonsters.Add(m); // List가 m의 주소(보관증)를 가져감
    }

    public void KillMonster(Monster m)
    {
        // ❌ [최악의 실수] 화면에서는 몬스터를 안 보이게 치웠지만,
        // AllMonsters 리스트에서 Remove를 안 하면 
        // GC는 "아직 리스트가 쓰고 있구나" 하고 몬스터를 절대 안 지웁니다
        
        // ⭕ [정답] 반드시 쌍으로 제거해야 합니다.
        AllMonsters.Remove(m); 
    }
}
```

## 5. Unity에서의 힙과 최적화

### 5.1 `Instantiate`와 `Destroy`의 진실
```csharp
using UnityEngine;

public class EnemySpawner : MonoBehaviour
{
    public GameObject enemyPrefab;

    public void SpawnEnemy(Vector3 pos)
    {
        // Instantiate는 내부적으로 거대한 new를 수행하여 힙에 오브젝트를 올립니다.
        GameObject enemy = Instantiate(enemyPrefab, pos, Quaternion.identity);
    }

    public void KillEnemy(GameObject enemy)
    {
        // Destroy를 부른다고 즉시 메모리에서 삭제되는 것이 아닙니다
        // "이번 프레임이 끝날 때 삭제해 줘"라고 예약표를 거는 행위이며,
        // 실제 힙 메모리에서의 수거(해제)는 훗날 가비지 컬렉터(GC)가 알아서 처리합니다.
        Destroy(enemy); 
    }
}
```

### 5.2 Stop-the-World 프레임 드랍과 오브젝트 풀링 (Object Pooling)
Unity 게임에서 매 프레임마다 `new Bullet()` 이나 `Instantiate()`로 총알을 만들고 파괴하면 어떻게 될까요?
1. 힙 메모리에 총알 객체가 어마어마하게 쌓입니다.
2. GC가 힙을 쓱 보고 "쓰레기가 너무 많네! 청소하자!" 하고 나섭니다.
3. **GC가 청소하는 동안 게임의 모든 실행(스레드)이 잠깐 멈춥니다! (Stop-the-World 현상)**
4. 유저는 "어? 렉 걸리네 프레임 끊기네!" 라고 느낍니다. (가비지 스파이크)

**[해결책: 오브젝트 풀링]**
새로 만드는(`new`) 대신, 시작할 때 미리 100개를 만들어 창고(Queue)에 넣어두고, 필요할 때 **꺼내 쓰고 다시 반납(재사용)** 하는 기술입니다.
```csharp
public class BulletPool
{
    private Queue<Bullet> pool = new Queue<Bullet>();

    public Bullet GetBullet()
    {
        if (pool.Count > 0) return pool.Dequeue(); // 1. 풀에 있으면 꺼내 쓴다
        return new Bullet(); // 2. 부족하면 할 수 없이 새로 만든다
    }

    public void ReturnBullet(Bullet b)
    {
        b.ResetStats(); // 3. 사용이 끝난 총알은 초기화 후
        pool.Enqueue(b); // 4. 다시 풀에 반납한다 (GC 수거 대상이 안 됨)
    }
}
```

## 6. 실습 문제 및 복습

**Q1. `int[] arr = new int[5];`를 선언했을 때 메모리 상황을 스택과 힙으로 나누어 설명하세요.**
> * **스택(Stack)**: `arr`라는 변수가 생기며, 힙에 만들어진 배열의 시작 주소(참조값)를 들고 있습니다.
> * **힙(Heap)**: `int` 데이터를 담을 수 있는 5칸짜리 연속된 메모리 공간(배열 객체 본체)이 할당되며, 각 칸은 `0`으로 초기화됩니다.

**Q2. 가비지 컬렉터(GC)의 역할과, 언제 객체를 수거해 가는지 설명하세요.**
> GC는 개발자 대신 힙(Heap) 메모리를 주기적으로 검사하여, **더 이상 스택이나 다른 객체에서 참조(접근)하고 있지 않은 고아 객체들(Garbage)** 을 찾아내어 메모리에서 자동으로 해제(수거)해 주는 관리자입니다.

**Q3. 게임에서 몬스터가 죽었을 때 이펙트(`GameObject`)를 무한정 `Instantiate`하고 `Destroy`하면 성능이 왜 떨어질까요? GC와 연관 지어 설명하고 해결책을 제시하세요.**
> 잦은 생성/파괴는 힙 메모리에 엄청난 양의 더미(Garbage) 데이터를 쌓게 만듭니다. 이를 청소하기 위해 GC가 자주 호출되면 **Stop-the-World** 현상이 발생해 게임 프레임이 뚝뚝 끊기는 렉(Stutter)이 유발됩니다.\
> ➔ **해결책**: 이펙트를 미리 여러 개 생성해 두고 활성/비활성화(`SetActive`)만 토글하며 재사용하는 **오브젝트 풀링(Object Pooling)** 패턴을 사용해야 합니다.

## 7. 주의사항 및 안전 습관

* **Update() 안에서의 `new`를 극도로 경계하라**: 매 프레임마다 무언가를 동적 할당하면 10초도 안 되어 GC 스파이크를 맞게 됩니다. 필요한 객체나 컬렉션은 `Start`나 `Awake`에서 미리 만들어 두고 재사용하세요.
* **Update() 안의 문자열 더하기(+) 금지**: 문자열(`string`)은 참조 타입이며 **불변(Immutable)** 입니다. `"Score: " + 10`을 하면 기존 글자를 뜯어고치는 게 아니라 힙에 새로운 문자열 객체를 턱턱 던져놓게 됩니다. UI 갱신은 점수가 바뀔 때만 하거나 `StringBuilder`를 쓰세요.
* **이벤트 구독(`+=`) 후 반드시 구독 취소(`-=`) 하기**: 이벤트 시스템에서 메모리 누수가 가장 많이 일어납니다. 객체가 파괴될 때(`OnDestroy`) 내가 남의 클래스에 걸어둔 구독을 해지하는 것을 잊지 마세요.
