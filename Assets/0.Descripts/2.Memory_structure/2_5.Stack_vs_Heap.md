# [메모리와 구조] 5. 스택(Stack) vs 힙(Heap) 완전 정복

## 1. 스택과 힙의 결정적 비교
C# 프로그램의 메모리 세계를 양분하는 두 거인, **스택(Stack)**과 **힙(Heap)** 의 결정적 비교입니다.

> **내 책상과 거대한 도서관 서고**
> * **스택 (Stack)** : 여러분의 **'책상'** 입니다. 지금 당장 처리할 서류들(지역 변수)이 깔끔하게 놓여있죠. 일이 끝나면(메서드 종료) 즉시 서류를 치워버리는 빠르고 체계적인 공간입니다.
> * **힙 (Heap)** : 거대한 **'도서관 서고'** 입니다. 책(객체)들은 크기도 제각각이고 빈 공간에 동적으로 꽂힙니다. 책을 찾으려면 스택(책상)에 놓인 **대출 카드(참조 주소)** 를 보고 직접 서고로 걸어가야 해요. 누군가 폐기 처리(가비지 컬렉터, GC)하기 전까지 책은 계속 그 자리에 있습니다.

**왜 이 차이를 알아야 할까요?**
값 타입(Value Type)은 책상 위 메모지처럼 직접 데이터를 쥐고 있고, 참조 타입(Reference Type)은 도서관의 책처럼 위치(주소)를 가리킵니다. 이 둘의 동작 차이를 이해하는 것이 C#의 기괴한 버그들을 막아내는 유일한 열쇠입니다.

## 2. 핵심 요약

| 구분 | 스택 (Stack) | 힙 (Heap) |
| :--- | :--- | :--- |
| **역할** | 메서드 흐름 제어, 지역 변수·매개변수 임시 저장 | 동적으로 생성된 객체(데이터 본체) 장기 보관 |
| **저장 데이터** | **값 타입의 본체** + **참조 타입의 주소(리모컨)** | **참조 타입의 본체** |
| **관리 방식** | OS / 런타임이 자동 관리 (LIFO 구조) | 가비지 컬렉터(GC)가 주기적으로 청소 |
| **크기 및 속도** | 작고 고정됨(~1MB) / **극강의 속도** | 크고 유동적(~수GB) / **할당·접근이 상대적으로 느림** |
| **생존 수명** | 메서드가 실행되는 동안만 (스코프 종료 시 소멸)| 프로그램 어딘가에서 주소를 참조하는 한 계속 생존 |

## 3. 세부 개념 및 원리

### 3.1 복사(Copy) vs 공유(Share)
* **값 타입 (`struct`, `int`...)** : 대입(`=`)하거나 메서드에 인자로 넘길 때, 메모리상의 데이터가 통째로 복사(Copy)됩니다. 원본과 사본은 완전히 남남입니다.
* **참조 타입 (`class`, 배열...)** : 대입(`=`)하거나 넘길 때, 스택에 있는 '주소(리모컨)'만 복사됩니다. 즉, 여러 변수가 힙에 있는 **단 하나의 객체를 공유(Share)** 하게 됩니다. 한쪽에서 수정하면 모두가 그 변화를 겪습니다.

### 3.2 `string`의 특별함 (불변성, Immutability)
`string`은 `class`로 만들어진 참조 타입이지만, 이상하게 값 타입처럼 안전하게 동작합니다.\
`s = s + "a"`를 실행하면, 힙에 있던 기존 글자를 뜯어고치는 것이 아니라, 힙에 아예 **새로운 문자열 객체를 새로 만들고** 스택의 주소를 그곳으로 갈아 끼웁니다. 원본이 변하지 않으므로 매우 안전합니다.

### 3.3 혼종의 함정: `struct` 안에 `class` 필드가 있다면? (얕은 복사)
```csharp
public struct BookData 
{ 
    public int PageCount;     // 값 타입
    public string AuthorName; // 참조 타입 (class)
}
```
이 구조체를 다른 변수에 대입(`=`)하면, 껍데기(`struct`)와 `PageCount`는 복사되지만, `AuthorName`은 **결국 힙의 같은 문자열 객체를 가리키는 '주소'만 복사**됩니다.\
이렇게 껍데기만 복사되고 알맹이 참조는 공유되는 현상을 실무에서는 **'얕은 복사(Shallow Copy)'** 라고 부릅니다.

### 3.4 박싱(Boxing)이 나쁜 이유 (메모리 관점)
`object obj = 10;` (박싱)\
스택에서 얌전히 빠르고 가볍게 놀고 있던 값 타입(`10`)을, 굳이 힙(Heap) 메모리에 새 방을 파서 이사시킨 뒤 스택에는 리모컨(주소)만 남깁니다. 할당 비용이 들고, 나중에 GC가 치워야 할 쓰레기가 되므로 게임에서는 박싱을 혐오합니다.

## 4. 코드로 보는 스택과 힙의 동작

### 4.1 누가 어디에 살고 있을까?
```csharp
void MyMethod()
{
    int a = 10;                         // 스택 (값 10 저장)
    Point p = new Point { X = 1 };      // Point가 struct라면 ➔ 스택 (값 통째로 저장)
    
    // player 변수 자체는 스택에 '주소'를 저장 / new Player() 본체는 힙에 뚝딱
    Player player = new Player();       
    
    // arr 변수는 스택에 '주소'를 저장 / new int[5] 배열 본체 5칸은 힙에 좌르륵
    int[] arr = new int[5];             
}
// 메서드가 끝나는 순간 스택에 있던 a, p, player, arr는 즉시 증발
// 힙에 남겨진 Player 본체와 배열은 곧 GC가 와서 치워버립니다.
```

### 4.2 흔한 실수: 구조체를 참조처럼 다루려 할 때
```csharp
public struct StatInfo { public int Power; }

// ❌ 매개변수로 받는 순간 '값 복사(사본)'가 일어남
void Buff(StatInfo stat) { stat.Power += 30; } 

StatInfo myStat = new StatInfo { Power = 50 };
Buff(myStat);
Console.WriteLine(myStat.Power); // 결과: 50 (사본만 80이 되었음)

// ⭕ 올바른 해결책
void BuffRef(ref StatInfo stat) { stat.Power += 30; } // 1. ref로 원본의 주소를 넘기거나
StatInfo BuffNew(StatInfo stat) { stat.Power += 30; return stat; } // 2. 새 값을 반환하거나
// 3. 아예 StatInfo를 class로 설계한다.
```

## 5. Unity에서의 스택과 힙 실전

Unity에서 매일 만지는 변수들의 정체를 정확히 알아야 버그를 막을 수 있습니다.

```csharp
using UnityEngine;

public class Player : MonoBehaviour
{
    // 아래 녀석들은 모두 struct(값 타입)입니다
    // 복사(Copy)되므로, 메서드 인자로 넘겨서 내부를 바꿔도 원본은 안 변합니다.
    public Vector3 position;       
    public Quaternion rotation;
    public Color tintColor;

    // 아래 녀석들은 모두 class(참조 타입)입니다
    // 주소가 공유(Share)되므로, 어디서든 하나를 바꾸면 모두가 바뀝니다.
    public GameObject weaponPrefab;
    public Transform myTransform;
    public Rigidbody rb;

    void Update()
    {
        // Vector3는 값 타입이므로, 바로 연산해서 대입할 수 있습니다.
        position = position + new Vector3(1, 0, 0);
        transform.position = position;

        // Rigidbody는 참조 타입이므로, 값을 바꾸면 힙에 있는 실제 물리 엔진 객체에 즉시 반영됩니다.
        if (rb != null)
            rb.linearVelocity = new Vector3(0, 5, 0); 
    }
}
```

## 6. 실습 문제 및 복습

**Q1. 값 타입과 참조 타입의 핵심 동작 차이를 한 단어씩으로 표현하면?**
> * **값 타입 (struct, int)** : **복사 (Copy)** ➔ 대입 시 데이터가 통째로 복사되어 서로 완벽히 독립합니다.
> * **참조 타입 (class, array)** : **공유 (Share)** ➔ 대입 시 주소(리모컨)만 복사되므로 같은 객체를 함께 바라봅니다.

**Q2. `string`은 분명 참조 타입(`class`)인데, 아래 코드에서 `s1`이 변하지 않는 이유는 무엇인가요?**
```csharp
string s1 = "Hello";
string s2 = s1;
s2 = "World";
```
> `string`은 참조 타입이지만 **불변(Immutable)** 이라는 특이한 성질을 갖습니다.\
> `s2 = "World"`를 실행하면, 힙에 있던 "Hello"를 뜯어고치는 것이 아닙니다. 힙에 "World"라는 새로운 문자열 객체를 새로 만들고 `s2`가 그 새 주소를 가리키게 만듭니다.\
> 따라서 `s1`은 원래 가리키던 "Hello"를 여전히 안전하게 쥐고 있습니다.

**Q3. 게임 캐릭터 능력치(힘, 민첩, 지능)를 `class`보다 `struct`로 만드는 게 유리한 이유를 '복사 오버헤드'와 '참조(메모리) 복잡성' 관점에서 설명하세요.**
> * **복사 오버헤드**: 능력치는 보통 정수 3~4개의 작은 데이터(16바이트 이하)이므로, 함수로 넘길 때 복사하는 비용이 CPU 입장에서 거의 0에 가깝습니다.
> * **메모리(참조) 복잡성**: 이를 `class`로 만들면 매번 `new`를 호출해 힙 메모리를 할당해야 하고, 안 쓰면 GC가 치워야 하는 부담이 생깁니다. 또한, 능력치 덩어리 자체를 통째로 덮어씌워 교체하는 상황이 많으므로 값 타입(struct)의 의미가 훨씬 자연스럽고 안전합니다.

## 7. 주의사항 및 안전 습관

* **변수에 무엇이 들어있는지 항상 의식하라**: "이 변수에는 데이터가 통째로 들어있나(`struct`), 아니면 힙으로 가는 리모컨만 들어있나(`class`)?"를 늘 스스로에게 질문하세요.
* **얕은 복사의 함정을 조심하라**: 클래스를 복사할 때 `A = B`라고 대입하면 복사가 아니라 "같이 쓰자!"가 됩니다. 진짜 복제본이 필요하다면 내부 데이터를 하나하나 새로 옮겨 담는 **깊은 복사(Deep Copy)** 로직(또는 `Clone()` 메서드)을 직접 구현해야 합니다.
* **박싱을 유발하는 코드를 피해라**: `int` 등 값 타입을 `object` 타입 변수나 컬렉션(예: 구시대 유물인 `ArrayList`)에 담지 마세요. 항상 제네릭(`List<int>`)을 사용해야 스택에서 빠르고 안전하게 놉니다.
